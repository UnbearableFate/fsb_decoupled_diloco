## 0. 结论

**计划整体设计是可实施的，但不能按当前文本直接开工。**

计划的权威链、writer 规则、故障模型、不变量 ID 和 requirement→test→gate→artifact 映射都写得比 plan 01 更完整，符合 `plans/ref/实施计划制定与 Agent 执行经验.md` 第 8 节的骨架要求。主要问题不在设计思路，而在于**计划与当前代码库的具体接触面没有被逐一核对**：有 10 处会直接阻断执行或造成静默失效的冲突，其中 4 处（B5、B6、B7、B8）属于"实现完成、测试通过、但正确性实际被破坏"的类型，不会自己暴露。

## 2. 阻断级问题（开工前必须修订）

### B1　`02-requirement-matrix.csv` 不存在

§15 声明"详细机器可读矩阵位于同目录的 `02-requirement-matrix.csv`。实施 agent 必须把每一行更新到对应报告证据"。

### B3　`allow_unsolicited_registration: false` 使 Phase 2 无法 bootstrap

§9.2 的默认配置为 `allow_unsolicited_registration: false`；§9.5 的 admission 事务第 3 步是"若 `launch_request_id` 已由另一个 instance fulfilled，拒绝当前 duplicate job"。

问题：正式实验的初始 8 个 learner 由 operator 的 PBS 作业启动（§12 G9："起始目标 8 个 learner"），它们**没有** `launch_request_id`，属于 unsolicited registration。按默认配置它们全部会被拒绝，run 永远无法启动。

计划全文没有定义 bootstrap 的 admission 路径——`launch_requests` 表（§9.4）只由 syncer 的扩容决策创建（§9.9 第 1 步）。

建议（择一并写进 §9.5）：

- 在 frozen config 中声明 `bootstrap_instances: 8`，syncer 在 `admission_state == open` 且已 admit 的 bootstrap 实例数 `< bootstrap_instances` 时接受无 request 的注册，超出后按 `allow_unsolicited_registration` 处理；
- 或把默认改为 `true`，由 `max_active_instances` 单独兜底，并明确说明该字段只用于"拒绝陌生主机注册"这一安全语义。

同时补一条 ID-xx 测试：`bootstrap 注册在无 launch_request 时被 admit，且超出 bootstrap 预算后被拒绝`。

### B4　learner 目前自己创建全局目录，违反 §2.3 的 writer 规则

事实：

- `fs_diloco/runtime/learner.py:1510` 和 `:2123` 都调用 `prepare_run_dirs(paths, config.sync.num_learners)`；
- `fs_diloco/storage/paths.py:131-148` 中该函数创建 `control/`、`weights/`、`optim/`、`updates/latest/`、`updates/payloads/`、`fragments/`、`heartbeats/`、`logs/`、`metrics/`，并为 `range(num_learners)` 的**每一个** learner 创建 payload 目录。

冲突：

- §2.3 规定"learner 只写以自己的 instance ID 命名的路径"，但当前 learner 会创建包括 `control/`（SQLite 与 latest/stop/summary 所在目录）在内的全部权威目录；
- §9.8 要求 discovery 不再依赖 `range(num_learners)`，但 learner 侧仍会按固定成员集预建目录，动态模式下这既无意义又会污染 pointer/payload 扫描面。

计划 §13.2 虽然列出了 `paths.py` 和 `learner.py`，但 §4 的不变量表和 §7/§11 的测试矩阵里都没有对应条目。

建议：新增不变量（如 `HA-21：非 leader 进程不创建或修改任何非自身 identity 命名的目录`），把 `prepare_run_dirs` 拆分为 `prepare_authority_dirs`（仅 leader 调用）与 `prepare_instance_dirs(instance_id)`（learner 调用），并在 P1-L2 的静态审查项里加入"learner 侧目录创建调用点"。

### B5　现有 learner watchdog 会在 takeover 完成前杀死所有 learner（最高优先级）

事实：

- `fs_diloco/runtime/learner.py:628-634`：`syncer_watchdog_timeout_seconds()` 在未显式配置时回落到 `liveness.no_progress_timeout_seconds`，默认 **600 秒**（`fs_diloco/core/config.py:105`）；
- `fs_diloco/runtime/learner.py:637-661`：`confirm_syncer_unresponsive()` 在超时且 `latest.json` 未出现更高 version 时返回 True；
- `fs_diloco/runtime/learner.py:1737` 与 `:2347`：learner 随即设置 `watchdog_stop_reason = "syncer_unresponsive"` 并进入受控停止。

冲突：§5.9 的恢复链路是「heartbeat seq 停滞 ≥ `heartbeat_stale_after_seconds`(30s) → mkdir claim → qsub candidate syncer → **PBS 排队** → 节点启动 → resume → 首次 commit」。在共享集群上仅排队一项就经常超过 600 秒。结果是 G5/G6 的正式验收里所有 learner 会先于新 leader 到位而自行退出，"8 learner 有效训练"（§8 G6）无法成立，且这种失败看起来像 learner 侧 bug，排查成本很高。

计划全文没有出现 `syncer_unresponsive`、`no_progress_timeout_seconds` 或 watchdog 的任何讨论。

附带问题：`confirm_syncer_unresponsive` 在 `paths.stop_json.exists()`（learner.py:652）时直接返回 False，把**任意** stop.json 当作合法抑制信号。§5.7 要求 learner 只接受 current epoch 的 stop，但这个调用点没有被列入需要改造的读取路径。

建议：

- 在 §5.6/§5.7 增加规则：learner 的 syncer 存活判定改为「观察到的最高 epoch heartbeat 的 seq 前进」，而非「latest version 前进」；只要存在未过期 lease 的 heartbeat，watchdog deadline 不推进；
- 增加 `recovery_wait_seconds`（覆盖 claim + PBS 排队的上界），并把它纳入 §5.1 的配置校验；
- 新增测试 `HB-05：syncer 暂停超过 no_progress_timeout 但存在有效 recovery claim 时，learner 不得以 syncer_unresponsive 退出`，纳入 G3；
- 把 `confirm_syncer_unresponsive` 的 `stop_json.exists()` 改为 epoch 校验，列入 §5.7 的读取规则清单。

### B6　GC 与 fencing 存在 TOCTOU：现有 checkpoint 回收是零 grace 的整目录删除

事实：`fs_diloco/storage/maintenance.py:84-127` 的 `collect_runtime_artifacts` 从 DB 构造 `keep_checkpoints`，然后对 `weights/`、`optim/`、`fragments/**` 下**所有**不在集合内的 `.safetensors` 直接 `unlink`。函数 docstring 明确写着"Global and fragment checkpoints have no grace because SQLite is authoritative"——这个前提只在单 writer 下成立。

冲突：旧 leader 在 lease 仍有效时进入 `run_maintenance`，扫描过程中 lease 到期、新 leader 完成 takeover 并提交了 N+1，旧 leader 的循环随后删除新 leader 的 live checkpoint。§5.4 只对"DB 外的短 cache 写"要求 `ensure_lease_remaining(min_remaining)`；HA-10 只禁止**已进入 fenced exit 后**执行业务 GC。两条规则都覆盖不了"开始时合法、执行中失效"的长扫描。

测试矩阵同样覆盖不到：DUAL-08 的操作是"old 在 GC 前暂停"，暂停点在扫描**之前**，恰好避开了这个窗口。

建议：

- §5.4 增加显式规则：GC 必须在每一批 unlink 之前重新校验 token（或按 `ensure_lease_remaining` 检查剩余租约 > 单批预期耗时），失败即中止并转入 fenced exit；
- 或更强：checkpoint 删除只允许删除由 fenced transaction 记录为 orphan 的路径，禁止"扫描目录 + 差集"式删除；
- 或最保守：对 checkpoint 引入 `lease_duration + max_clock_skew` 的 grace，代价是 current-only 集合会短暂多出一份；
- 把 DUAL-08 改为"old 在 **GC 扫描循环中间**暂停"，并新增通过条件"new epoch 的 current weight/outer 在旧 leader 恢复后仍存在且 checksum 不变"。

### B9　31 个 store 写方法中 25 个是 autocommit，没有可 fence 的事务边界

对 `fs_diloco/storage/sqlite_store.py` 的全量统计：

- 含写语句的方法：**31** 个；
- 使用显式 `BEGIN IMMEDIATE` 的：**6** 个——`initialize_full_run`(222)、`commit_full_merge`(271)、`insert_update_metadata`(520)、`prepare_full_resume`(729)、`delete_archived_rows`(1012)、`insert_fragment_update_metadata`(1156)；
- 其余 **25** 个为裸 `conn.execute(...)` + `conn.commit()`，包括 `set_run_state`(141)、`upsert_global_version`(158)、`upsert_learner`(437)、`update_learner_status`(490)、`mark_updates_selected`(654)、`mark_updates_applied`(676)、`reset_selected_to_pending`(705)、`reset_all_selected_to_pending`(717)、`drop_updates`(797)、`drop_obsolete_updates`(819)、`drop_ineligible_updates`(837)、`finalize_unconsumed_updates`(870)、`drop_superseded_updates`(888)、`clear_gc_pending_paths`(1069)，以及全部 8 个 `*_fragment_*` 变体。

§5.4「每个业务 transaction 在 `BEGIN IMMEDIATE` 后、任何写入前调用 `_assert_current_leader_in_transaction(token)`」在计划里只占 P1-L2 的一行，但实际是 Phase 1 中最大的单项改造：25 个方法需要从 autocommit 改写为显式事务并加 fence。

同时存在一个未解决的语义冲突：§3.1 规定 fragment 模式"保持现状并回归"、"配置 fail closed"，但 fragment mutator 与 full mutator 共用同一个 `SQLiteStore`。计划没有说明 fragment 路径下 token 是可选、是 no-op sentinel、还是 store 被拆成两个类。

建议：

- 把 B9 从 P1-L2 的一行提升为独立工作单元（如 P1-L2a「事务边界统一」、P1-L2b「fence 注入」），并在计划里附上上述 31 个方法的清单作为完成度检查表；
- 明确 fragment 模式的 token 语义，并在 FENCE-01..06 之外补一条 `FENCE-07：fragment 模式下 store 行为与 plan-01 基线逐字节一致`。

### B10　`connect()` 无条件建表/ALTER，与 §5.2 冲突且使 pre-HA 检测不可靠

事实：`fs_diloco/storage/sqlite_store.py:58-74` 的 `connect()` 在**每次打开**时执行 `conn.executescript(_schema_text())`（全部 `CREATE TABLE IF NOT EXISTS`），随后无条件调用 `_ensure_resource_columns(conn, "updates")`、`_ensure_resource_columns(conn, "fragment_updates")`、`_ensure_full_update_metadata_columns(conn)`——即 §5.2 明令禁止的"一组无条件 `ALTER TABLE`"。

进一步后果：所有消费者（syncer、analysis 工具、Checker、测试）都走这个 `connect()`。一旦把 `syncer_leader` / `syncer_epochs` 加进 `schema.sql`，**只是打开一个 pre-HA run 做离线分析**就会在其中创建这些表。因此"表是否存在"永远不能作为 pre-HA 的判据，而 §3.2 与 HA-18 要求 pre-HA resume 必须 fail closed。

建议：

- 在 `initialize_full_run` 的同一事务内写入 `run_state['schema_version']`（该表已存在且已有 `identity`/`config`/`resume_generation`/`summary` 四个键）；resume 时以该键缺失或版本不符作为 fail-closed 依据，而不是以表存在与否判断；
- 把 `connect()` 的 DDL 改为受控迁移入口（显式 `migrate=True` 参数或独立函数），只读消费者不触发 DDL；
- 为此补测试 ID，如 `SCHEMA-01 新 run 写入 schema_version`、`SCHEMA-02 pre-HA run resume fail closed`、`SCHEMA-03 只读打开 pre-HA DB 不产生 HA 表`。§5.2 目前只有文字要求，测试矩阵中无对应条目。

## 3. 设计缺口（建议在 L0 冻结时解决）

### D1　`candidate_wait_seconds` 语义未定义

该字段在 §5.1 的 YAML 中出现一次（`candidate_wait_seconds: 180.0`），此后全文再未出现：不在同节的校验规则里，不在 §7 的任何测试中，也不在 §5.8 的生命周期描述里。

同时，计划没有规定候选 syncer 重试 acquire 的频率。候选每次 acquire 都要 `BEGIN IMMEDIATE`（§5.4），会与在任 leader 的 merge 提交争抢 writer 锁（`synchronous=FULL` + `journal_mode=DELETE`，每次提交多次 fsync）。

建议：定义为"候选在放弃前等待 leadership 的上限"，并规定候选**先读 heartbeat 文件**、仅在观察到 lease 疑似过期后才尝试 DB acquire，避免周期性写锁争抢。加入 LEASE-11 测试：在任 leader 存在时，候选轮询不使 leader 的 `sqlite_commit_seconds` p99 上升超过约定比例。

### D2　`busy_timeout` 与 lease 时序未纳入配置校验

`fs_diloco/storage/sqlite_store.py:61,68` 设置 `sqlite3.connect(timeout=60.0)` 与 `PRAGMA busy_timeout=60000`。以 §5.1 的起始值（`renew_interval=10s`、`lease_duration=90s`）计算，一次 renew 可能在锁上阻塞 60 秒——相当于 6 个 renew 周期；`ensure_lease_remaining()` 同样可能阻塞到 lease 过期之后。

建议：lease/renew 使用**独立且短超时**的连接（`busy_timeout ≈ renew_interval`），并把关系加入 §5.1 的校验集：`lease_busy_timeout_ms <= renew_interval * 1000`。DUAL-09 的通过条件应写成具体数值而非"超阈值时安全 fence"。

### D3　leader 自身的剩余租约应基于 monotonic 时钟

§5.6/§5.7 已正确要求 learner 用本地 monotonic 时间判定 heartbeat 停滞。但 §5.4 的 `ensure_lease_remaining(min_remaining)` 未说明时基。若它比较 `time.time()` 与 DB 中的 `lease_expires_at`，则 leader 节点的一次 NTP 跳变会静默延长或缩短它自认的租约，而这正是 fencing 的最后一道防线。

建议：明确 leader 记录 `monotonic_at_last_successful_renew`，剩余租约 = `lease_duration - (monotonic_now - 该时刻)`；DB 中的 wall-clock `lease_expires_at` 仅供**其他节点**做 takeover 判断。对应 LEASE-10 应补一个"leader 本地时钟跳变不改变其自评剩余租约"的用例。

### D4　`format_version` 语义冲突

`fs_diloco/core/constants.py:5` 定义 `FORMAT_VERSION = 1`，并被 `liveness.py:32`（heartbeat）、`modeling/param_index.py:50`、`runtime/syncer.py:945`（update metadata）强校验。§5.6 的 syncer heartbeat 示例硬编码 `"format_version": 2`。

若全局提升到 2，上述三个校验点会拒绝所有 pre-HA 产物，与 §3.2 的"pre-HA run 的历史分析继续可读"冲突。

建议：新增独立常量 `SYNCER_HEARTBEAT_FORMAT_VERSION = 1`（新文件类型从 1 起算），或明确全局提升并逐一列出需要放宽为"接受 1 或 2"的读取点。在 L0 显式冻结。

### D5　动态模式的数据分片数没有定义（影响正确性，不只是质量）

事实：`fs_diloco/modeling/hf_data.py:160` 使用 `dataset.shard(num_shards=num_learners, index=learner_index, contiguous=True)`，`:167` 用 `learner_index` 作为 shuffle 种子。

§9.1 说 `stream_id` 用于"dataset shard/iterator seed"，但**没有定义动态模式下 `num_shards` 取什么值**。`max_active_instances=16` 而 `desired_contributors=8`：按 8 分片则第 9 个被 admit 的实例无 shard 可用，或必须与他人共享同一 shard（同一数据被两个 current stream 重复训练，MEM-18 的"每个 current stream 最多贡献一份 proposal"无法阻止这种重复）；按 16 分片则与 static 基线的数据分布不同，§14.2 的"训练质量比较另行报告"也就失去了可比基线。

建议：新增配置 `membership.stream_space_size`（分片总数），校验 `stream_space_size >= max_active_instances` 且 `>= desired_contributors`；`stream_id ∈ [0, stream_space_size)`。补测试 `ID-11：任意时刻不存在两个 current instance 持有同一 stream_id`，纳入 G7。

### D6　`productive_instances` 的窗口数 `W` 与 ETA 来源未定义

§9.10 定义"最近 W 个 window 有贡献，或 heartbeat fresh 且预计下一次 upload 尚未逾期"。`W` 没有配置字段、没有默认值、没有校验；"预计下一次 upload" 的来源也没有指名（现有实现中最接近的是 `fs_diloco/runtime/syncer.py:1197` 的 `fastest_next_upload_eta_seconds`）。

SCALE-08/SCALE-09 直接依赖这两个量，无法在不确定 `W` 的情况下写出确定性测试。

建议：加入 `scaling.contribution_window_count: 2`（或类似）并在 §9.2 的校验中约束；在 §9.10 中显式指名 ETA 计算函数。

### D7　launch-request TTL 过期不会取消已排队作业，存在容量超发

`launch_request_ttl_seconds: 900`（§9.2）+ LR-06「TTL 内计 reserved capacity，过期后可重试」+ §3.3「不实现主动 scale-in 或为节省资源而 qdel」+ `allow_qdel_superseded_job: false`。

在繁忙队列上：request A 排队 >15 分钟 → TTL 过期 → reserved capacity 释放 → 创建 request B → A 与 B 先后启动 → 实际容量超过 `desired_contributors`。MEM-11 只保证"同一 logical request 不产生重复有效容量"，跨 request 的超发不在其覆盖范围内。

建议：把 TTL 的语义改为"仅当 `qstat` 已查不到该 job 时才判定过期"；只要 job 仍处于 queued/running，无论多久都计入 reserved capacity。在 §14.2 补一条上界："任意时刻 admitted instances + reserved capacity ≤ `max_active_instances`"，并写入 Checker。

### D8　§5.9 的 attempt 编号在多 learner 之间不一致，HA-14 按现文本不成立

§5.9：「attempt 由 stale elapsed time 除以 `recovery_claim_interval_seconds` 得到」。每个 learner 的 "stale elapsed" 以**自身**开始观察停滞的时刻起算（§5.6 要求记录本地 monotonic 时间）。两个启动时间相差 30 秒的 learner，对同一次真实故障会算出不同的 attempt 序号，各自 `mkdir` 成功，于是同一次故障产生多个 winner——而 HA-14 声称"同一 stale heartbeat observation/claim attempt 最多有一个 claim winner"。

CLAIM-01（8 learner 同时 claim）之所以能通过，是因为测试设定它们"同时"观察，掩盖了这个问题。

建议（择一）：

- 把 attempt 改为由**共享量**导出：`floor((now - heartbeat.timestamp) / recovery_claim_interval_seconds)`，其中 `heartbeat.timestamp` 是所有 learner 读到的同一个值（代价是引入对 wall clock 的依赖，需与 `max_clock_skew_seconds` 一起论证）；
- 或接受重复候选，把 HA-14 改写为"重复 claim 至多产生 N 个候选（N ≤ active learner 数），且至多一个成为 leader"，并把 CLAIM-01 的用例改为**错峰观察**。

第二种更诚实，也与 §2.4 中"PBS 不提供通用 exactly-once qsub"的立场一致。

### D9　checkpoint checksum 成本未纳入性能预算

§5.2 新增 `weight_sha256` / `optim_sha256` 列，§5.5 要求"已存在且 checksum 不同则 fail closed"。

现状：`io.compute_sha256` 默认 `False`（`fs_diloco/core/config.py:152`），且当前只在 learner 侧对 proposal payload 使用（`learner.py:1388,1474`）。syncer 从不计算 checkpoint 的 sha256。对 GPT-2 规模的 weight+outer，这是新增在 publish 关键路径上的全量读取。

§14.1 的预算只覆盖"lease/heartbeat 累计 wall time < 3%"，没有覆盖 publish 路径的回归。

建议：把 checksum 改为**惰性**——仅当目标路径已存在时才计算并比较（正常路径下目标不存在，零成本）；并在 §14.1 增加一条"publish p99 相对 plan-01 基线回归 ≤ X%"。

### D10　`published_by_epoch` 拒绝规则需要有界等待

§5.7 规则 2：learner 忽略 `published_by_epoch` 低于最高观察 epoch 的 cache 并"等待 leader repair"。§5.8 的"resume 先重建 latest，再发布 active heartbeat"顺序大幅缩小了这个窗口，方向正确。

剩余风险：新 leader 在 acquire 成功、写入 `syncer_epochs` 之后、重建 latest 之前崩溃时，learner 已可能通过其他途径观察到更高 epoch，从而永久拒绝当前有效的 latest。计划没有定义这个等待的上界，而其唯一兜底恰好是 B5 中会误杀 learner 的 watchdog。

建议：在 §5.7 明确"忽略低 epoch cache 的最长等待"，并说明超时后的行为（继续等待并计数 `cache_rejected_lower_epoch_count`，而非退出）。与 B5 的修订一并处理。

### D11　动态模式下 `sync.quorum_max` / `sync.num_learners` 的关系未定义

`fs_diloco/core/config.py:388-391`：传入 `--num-learners` 时会把 `quorum_max` 和 `quorum_min` 双双 clamp 到 `num_learners`。

§3.2 规定"dynamic 配置不得使用该字段定义成员权威"，§9.2 的校验只涉及 `desired_contributors >= sync.quorum_min`。但 `quorum_max` 决定单次 merge 最多选取多少 proposal：若 `num_learners=8` 而 `max_active_instances=16`，第 9 个 admitted instance 的 proposal 永远无法在同一次 merge 中被选中。

建议：在 §9.2 增加校验 `sync.quorum_max >= desired_contributors`，并规定 dynamic 模式下 `quorum_max` 由 `desired_contributors`/`max_active_instances` 导出、`sync.num_learners` 被显式拒绝或忽略（并记录 warning）。

## 4. 集群执行风险（G4 之前必须确认）

### S1　9 个独立 PBS 作业的共调度问题

现状：正式实验使用单作业 + 单次 `mpirun`——`scripts/miyabi/run_9node_gpt2_wikitext2_5000steps.pbs` 的 `#PBS -l select=9:mpiprocs=1`（第 5 行）与第 142-147 行的 `mpirun -np "$NNODES"`，各 rank 按 `OMPI_COMM_WORLD_RANK` 分角色。

计划 G5/G6/G8/G9 要求按角色拆成独立作业。在没有预约（reservation）的情况下，1 个 syncer 作业 + 8 个 learner 作业各自独立排队：部分启动时 run 会长时间低于 `quorum_min`，而 Phase 2 的扩容滞回恰好会因此触发（连续两个 window `eligible <= 6`）并提交**更多**作业，形成正反馈。

建议：

- 在 P1-L0 中把"作业编排形态"列为必须冻结的决策：job array / 每角色独立作业 / 一个 N 节点的 learner pool 作业；
- 在 §9.10 的触发条件中增加 `now >= initial_membership_deadline`——初始成员集齐或截止之前禁止扩容；
- §12 G9 目标是 9 节点，但 Phase 2 必然要再启动一个扩容 learner，计划未说明这第 10 个节点从哪来。需明确（例如起始只用 7 个 learner，留 1 个节点给 scale-out）。

### S2　独立作业的 run 发现与源码一致性没有协议

现状：所有 rank 由同一个 shell 传入 `--run-id / --shared-root / --config / --learner-id`（`fs_diloco/runtime/learner.py:182-186`）。

独立作业需要一个显式的交接协议：learner 作业**在注册之前**如何得知 `shared_root` 与 frozen config？§9.5 的 admission JSON 里有 "config/source fingerprint"，但那是 admission 的**输出**，解决不了注册前的发现问题；计划也没说 fingerprint 不匹配时是拒绝还是告警。

建议：定义 `<shared_root>/control/run_descriptor.json`（run_id、config 路径、source fingerprint、bootstrap 预算、admission 端点约定），由 leader 在 v0 之后原子写出；learner 作业只需通过环境变量拿到 `shared_root`。source fingerprint 复用已有的 `scripts/miyabi/capture_source_identity.py`，不匹配一律拒绝（ref 文档 §6.4："不要让 live job 在不同节点加载不同源码版本"）。

### S3　`--learner-id` 目前是必填参数

`fs_diloco/runtime/learner.py:185`：`parser.add_argument("--learner-id", required=True)`。动态模式下 learner 必须自行生成 identity，该参数需变为可选或被拒绝。§13 未列出 CLI 接口变更，建议补一小节"CLI/接口变更"。

### S4　共享 FS 上的多写者 SQLite 争抢尚未被现有探针覆盖

`scripts/miyabi/sqlite_shared_fs_probe.py` 已经覆盖 stress、kill-reopen、跨节点可见性（子命令见其 `parse_args`），但没有**并发争抢写者**模式——而这正是 HA 引入的新风险（多个候选同时 `BEGIN IMMEDIATE`）。

§13.1 计划新增 `scripts/miyabi/syncer_lease_shared_fs_probe.py`。建议改为**扩展既有探针**（新增 `contend` 子命令：N 进程跨节点并发 acquire/renew，记录 busy 次数、锁等待分布、`BEGIN IMMEDIATE` 的 starvation），避免两个近乎重复的探针各自漂移。

### S5　`miyabi-development` skill 在当前环境不可见

事实：根 `AGENTS.md:5`、本计划第 17 行、`plans/DONE/imp_plans/01.md:3` 都引用该 skill，但本次检出的仓库与 `~/.claude` 下均无对应的 skill 定义。

这可能只是本地静态审查环境的差异（实施在 Miyabi 登录节点进行）。建议在 G0 的检查项中加入"确认 `miyabi-development` skill 可用"，否则 G2 及之后的全部计算节点门禁都会在开始时被阻断。
