#### M1 — FEAS-01's writer-lock pause boundary is demonstrated only within a single node

**Evidence.** `plan02_fault_probe.py:125-232` implements `writer_lock_probe` entirely as a local parent/child pair: the holder is launched with `subprocess.Popen` (`:130-140`), stopped with `os.kill(child.pid, SIGSTOP)` (`:143`), and the contender is an in-process `sqlite3.connect` in the same process (`:151-161`). `run_plan02_phase0_feasibility.pbs:130-133` runs this probe once, un-wrapped by `mpirun`, so it executes only on the primary host. The retained artifact confirms one host: `sqlite_writer_lock.hostname = "mg0004"` with no contender-host field. The Checker (`check_plan02_feasibility.py:52-98`) asserts nothing about hosts for FEAS-01, unlike FEAS-03 where `host_count >= 2` and `writer_hostname != reader_hostname` are enforced (`:157`, `:167-172`, `:180-184`).

**Why it matters.** Plan §2.3 defines the availability boundary for a *leader on another node* that pauses inside a write transaction, and §10.1 P0-L1 / §15 both call for "1/2 节点证据" for the writer-lock pause boundary. The property Phase 1 depends on — that a stopped in-transaction writer on host A blocks a candidate on host B, and that killing it releases the lock for host B — is exactly the property a shared filesystem is most likely to break. The single-node result does exercise the shared-FS locking backend (the probe DB lives under `/work/.../reports/DOING/.../artifacts/work_*/`), and the 8-writer/2-host `contend` run gives strong indirect cross-node locking evidence (1521 handled busy events, 400/400 commits, max wait 2.945 s, integrity `ok`). Neither substitutes for a cross-node SIGSTOP/SIGKILL counterexample.

**Fix.** Add a two-rank `mpirun --map-by ppr:1:node -np 2` stage that runs the holder on rank 0 and the contender on rank 1 against one shared DB, exchanging readiness through the existing work directory; record `holder_hostname`, `contender_hostname`, and `successor_hostname` in the FEAS-01 evidence, and add Checker assertions `holder_hostname != contender_hostname` and `host_count >= 2` mirroring `check_plan02_feasibility.py:167-184`.

## 3. Correctness, regression, error handling, invariants, coverage

### 3.1 Correctness of the new logic (verified by reading and re-derivation)

- **Clock offset interval (`sqlite_shared_fs_probe.py:352-362`) is mathematically correct.** With `T1 = local_sent`, `T2 = remote_received`, `T3 = remote_sent`, `T4 = local_received`, causality gives `θ ∈ [T3 − T4, T2 − T1]` for `θ = remote − local`; the code computes exactly `lower = remote_sent − local_received` and `upper = remote_received − local_sent`. The 20-round intersection (`max` of lowers, `min` of uppers, `:520-522`) and `absolute_offset_upper_bound = max(|lower|, |upper|)` are the correct conservative summary. Filesystem transport delay inflates the interval, so the bound errs safe. Measured result `[-0.003513105, +0.003404724] s` against a 2 s budget is comfortable, and the unit test at `tests/test_sqlite_probe.py:148-157` pins the asymmetric-delay case.
- **Writer-lock probe conclusions are sound for the single-node case.** Uncommitted-row invisibility is read through a `mode=ro` connection before the kill (`plan02_fault_probe.py:171-179`); the successor path proves rollback plus a fresh commit; `holder_exit_status == -9` proves the release was by SIGKILL, not a graceful commit. Any deviation raises rather than being reported as PASS (`:166-169`, `:178-179`, `:204-205`).
- **FEAS-02 canonical selection is genuinely per-kind.** `_select_highest_epoch` (`:296-308`) raises on an empty discovery set, so a silently-empty glob cannot pass; `canonical_discovery_counts` (`:395-400`) plus the Checker's `>= 2` per kind (`check_plan02_feasibility.py:136-143`) enforce non-emptiness of the scan itself. Retained evidence shows all three fixed caches clobbered to epoch 1 while all three canonical selections are epoch 2, then repaired to 2.
- **Scheduler classification.** `classify_scheduler_state` (`plan02_pbs_capability.py:53-74`) separates `query_failed` (None) from `no_record` ({}), maps `Q/H/W` → queued (which is what makes the `-a <future>` scalar produce deterministic queued evidence), `R` with `substate < 42` → prologue, `S` → suspended. The retained scalar job shows real `queued → prologue → running → finished` observations, and the array's two physical children carry `Exit_status=0`, `run_count=1`, `Rerunable=True`.
- **`_wait_for_child` cannot be satisfied by a marker alone** (`:240-244`): completion requires the expected artifact count *and* a terminal query with `Exit_status == 0`; `tests/test_plan02_feasibility.py:178-210` pins the marker-plus-exit-7 case.

### 3.3 Error handling and fail-closed behavior

- The Checker catches `BaseException` and emits `BLOCKED` with the offending input retained (`check_plan02_feasibility.py:302-321`), never PASS-by-exception; stdout is strictly `PASS\n` or `BLOCKED\n`; exit code 0/1. Verified by test and by re-running it against the retained blocked input.
- The PBS `ERR` trap (`run_plan02_phase0_feasibility.pbs:55-115`) synthesizes a structured failure input, runs the Checker on it, and persists `${STAMP}_phase0-feasibility_blocked.json`. This path was genuinely exercised: `20260806-090551_phase0-feasibility_blocked.json` records `probe_failure.failed_line = 267` (the aggregation call) and 68 individual requirement failures — i.e. missing evidence maps to `BLOCKED` per requirement, as plan §1.3 demands.
- Cleanup is guarded twice by a resolved-prefix `case` match on `"$RESOLVED_ARTIFACT_DIR"/work_*_"$JOB_ID_SHORT"` (`:47-53`, `:301-310`), and only runs after `PASS`; `STAMP` is constrained to `^[0-9A-Za-z][0-9A-Za-z-]*$` before path construction (`:21-24`). This directly addresses the attempt-1 `rm -rf "$WORK_ROOT"` near-miss recorded in `failures.md`.
- Gaps: preflight failures before the trap is installed (`exit 2` at `:34-43`, `:47-53`) produce no structured artifact — acceptable, since they also produce no PASS artifact. If the Checker process were killed before printing, `CHECK_STATUS` would be empty and the subsequent copy heredoc would fail into the `ERR` trap, still yielding `_blocked.json`.
- All JSON writes across the five new scripts use `mkstemp` + `fsync` + `os.replace` in the destination directory, so readers and globs never observe partial files; child artifacts use the same pattern and the parent's glob `child_*_*.json` cannot match the dot-prefixed temp names.

### 3.4 Concurrency and persistence invariants

- **Serialization**: `contend` (`sqlite_shared_fs_probe.py:207-345`) exercises 8 cross-node writers × 50 `BEGIN IMMEDIATE` transactions with a 5 ms in-lock hold and a 10 ms busy timeout under a 60 s bounded retry loop; every `OperationalError` that is not `locked`/`busy` is re-raised. Evidence: 400 requested = 400 committed = 400 DB event rows, 8 distinct DB writers over 2 hosts, 38 acquire + 362 renew, 1521 handled busy events, 0 starvation, `integrity_check = ["ok"]`, `journal_mode=delete`, `synchronous=2`. The equality `requested == committed == event_count` is the invariant that would expose a lost update from a hypothetical second concurrent writer, and the Checker enforces it (`check_plan02_feasibility.py:185-193`).
- **Schema ownership**: `contend` opens with `open_existing` (`:83-97`), which refuses a missing file and never issues DDL; only the parent's one-shot `verify` creates the schema. `verify-readonly` uses a `mode=ro` URI and cannot create a DB (`:106-110`, pinned by `tests/test_sqlite_probe.py:160-169`). This matches the plan §2.4 rule that candidates must not execute DDL.
- **Cross-node visibility**: writer on `mg0004` (25 transactions) and reader on `mg0005` observe identical `counter`/`events`, with the Checker requiring distinct hostnames.
- **Publication ordering**: the FEAS-02 probe reproduces the plan §2.2 model exactly — lease check → SIGSTOP with staged temp files → new epoch publishes canonical + fixed cache → SIGCONT `os.replace` clobbers the fixed cache → reader still selects the highest epoch canonical → leader repairs. One forward-looking note (not a Phase 0 defect): `_select_highest_epoch` trusts `published_by_epoch` from the payload and does not cross-check it against the epoch directory name or `published_by_owner_id`; Phase 1's real reader must validate both, or a stale writer could advertise a higher epoch inside its own directory.
- **Process lifecycle**: both fault probes CONT-then-KILL their child in `finally` (`plan02_fault_probe.py:226-231`, `:402-407`). A hard kill of the supervisor between SIGSTOP and the `finally` could leave a stopped child until PBS reaps the job tree — already dispositioned as deferred to Phase 1 P1-L1 (`progress.md:266`), which I consider reasonable.
