### FSD-R2 — Medium — the ingest whitelist makes transient SQLite failures candidate-fatal, exceeding the accepted FSD-M5 direction

**Violated invariant.** Schema, command-conflict and stale-leader integrity failures must not be swallowed — but nothing in the accepted direction asks for retryable storage faults to terminate the only syncer.

**Evidence (observed).**
- `fs_diloco/runtime/syncer.py:850-852` — `except (AuthoritySchemaError, CommandConflictError, StaleLeaderTokenError): raise` then `except (MembershipFenceError, OSError, ValueError) as exc:`; `:873-875` the same with `ProposalPayloadError` added.
- The base swallowed everything with `except Exception`. The remediation implemented the narrowing as a **whitelist**, not as a blacklist of the three named classes.
- `fs_diloco/storage/authority.py` contains no `except sqlite3` handler; command operations propagate raw driver exceptions. I verified `sqlite3.OperationalError.__mro__` is `(OperationalError, DatabaseError, sqlite3.Error, Exception, …)` and `issubclass(sqlite3.OperationalError, (OSError, ValueError))` is `False`.
- Two concurrent writers exist on the shared-filesystem database: the main leader connection and `_LeaseRenewer._run` (`fs_diloco/runtime/syncer_entrypoint.py:62-75`), with `business_busy_timeout_ms: 5000`.
- `scripts/miyabi/run_full_protocol_rank.sh:161-172` — for `none` and `learner_replacement`, rank 0 runs exactly one `run_syncer`; there is no successor process.

**Concrete counterexample.** During the 9-node formal run, the `INSERT INTO cycle_receipts` inside `ingest_cycle_receipt` (`fs_diloco/storage/authority.py:1336-1347`) raises `sqlite3.OperationalError: database is locked` (or `disk I/O error` on the shared FS) after the 5-second busy timeout. Previously this produced one `receipt_ingest_rejected` telemetry event and the next loop iteration re-ingested the same durable receipt file. Now it escapes `_ingest_proposals`, is caught only by the candidate error boundary (`syncer_entrypoint.py:240-256`), fences the epoch as `error`, and `run_syncer` returns nonzero — the run dies with no successor and the gate fails.

**Smallest current-only fix.** Keep the explicit `except (AuthoritySchemaError, CommandConflictError, StaleLeaderTokenError): raise` clause and restore the second clause to `except Exception as exc:` in both handlers. That implements exactly the accepted FSD-M5 wording with no collateral reclassification.

**Missing test / durable oracle.** Inject `sqlite3.OperationalError` from a fake `ingest_cycle_receipt` and assert `_ingest_proposals` returns normally after emitting `receipt_ingest_rejected` — pairing with the propagation tests so the boundary between "terminal integrity failure" and "retryable storage fault" is pinned in both directions.

*Inference, stated separately:* if the team deliberately prefers fail-fast on any storage fault, that is a defensible policy, but it is a scope change beyond the disposed finding and should be recorded as such rather than arriving as a side effect of a narrowing.

### FSD-R7 — Low — the new `finally` block can replace the primary candidate failure with a release failure

**Violated invariant.** Stale-leader integrity failures must surface as themselves; the epoch projection is the fault oracle.

**Evidence (observed).** `fs_diloco/runtime/syncer_entrypoint.py:257-264`. `candidate_failed` is set only *after* `authority.fail_leader(token)` succeeds (`:252-253`). `release_leader` raises `StaleLeaderTokenError` via `_verify_token` (`fs_diloco/storage/authority.py:998-1002`), and it writes `final_state='released'` (`:1012`) whereas `fail_leader` writes `final_state='error'` (`:1038`).

**Concrete counterexample.** `run_fenced_syncer` raises `AuthoritySchemaError` (exactly the class FSD-M5 made terminal). `authority.fail_leader(token)` at `:252` raises against the same damaged database, so `candidate_failed` stays `False` and a note is attached. The `finally` block then calls `release_leader(token)`. Two outcomes, both wrong: if it raises, that exception replaces `AuthoritySchemaError` as the propagating exception (the original survives only as `__context__`); if it succeeds, the failed candidate's epoch is durably recorded as `released` instead of `error`, corrupting the exact `syncer_epochs.final_state` tuple that `check_full_protocol_run.py:650` uses as the takeover oracle. The mislabelling path is pre-existing; the exception replacement is newly introduced by this increment.

**Smallest current-only fix.** Set `candidate_failed = True` unconditionally in the error boundary (before attempting `fail_leader`), so a candidate that entered its error path can never take the release path; and wrap the `release_leader` call so a failure is attached as a note to the in-flight exception rather than raised from `finally` — while still raising when there is no in-flight exception (which is what the new `test_successful_candidate_does_not_swallow_release_failure` pins, and which remains correct).

**Missing test / durable oracle.** A candidate whose body raises and whose `fail_leader` also raises must propagate the body's exception type and must leave `final_state` not equal to `'released'`.
