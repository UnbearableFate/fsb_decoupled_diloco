## Executive conclusion

All three failures are valid harness-domain attempts, but none is evidence of a
production runtime defect. Attempts 1 and 2 closed repository-precondition
gaps. Attempt 3 exposed a faulty mutation probe: it asked SQLite to persist a
row forbidden by the current schema, so the exception occurred before the
Checker subprocess and did not test Checker sensitivity.

The required logic rewrite is to create a schema-valid but workload-invalid
receipt by changing both processed and effective tokens from 16 to 15 in one
transaction, assert that exact row was committed, and require the Checker error
`at least one durable receipt has the wrong cycle workload`. This exercises the
intended durable oracle without disabling database constraints or changing the
acceptance requirement.

## End-to-end data and control flow

1. The harness resolves the current functional config, binds the current Git
   source identity and initializes one fresh run descriptor/schema.
2. A fenced `LeaderAuthority` creates genesis, ingests one current cycle
   receipt/proposal, selects it, commits version 1, terminalizes the contributor
   and finalizes terminal authority.
3. `ControlPublisher` projects that committed terminal row to the immutable
   epoch stop and fixed stop/summary caches. The harness then publishes current
   source/init/summary logs, an audit batch and actor attestations.
4. Each mutation changes one durable input after the valid fixture is complete.
   The Checker is a separate process that reopens the authority read-only,
   checks SQLite integrity/schema/identity, merges hot and archived history,
   validates terminal controls/topology/workload/object identities, and
   atomically publishes PASS or FAIL evidence.
5. Attempt 3 executed only
   `processed_tokens_this_cycle=15`. SQLite enforces
   `processed = effective + local_discarded`; the other values remained 16 and
   0. Constraint evaluation rejected the statement inside the context-managed
   transaction and rolled it back. `_run_checker` was never called, so there is
   no Checker classification to interpret.

## Oracle assessment and alternatives

The test's intended invariant is correct: a registered one-step, one-learner
run must contain exactly 16 processed/effective tokens in its only receipt. The
Checker already compares every receipt to the config-derived per-update token
count and independently compares receipt totals with token rollups.

Considered alternatives:

- Disabling CHECK constraints would manufacture database corruption that
  `PRAGMA integrity_check` can reject before the workload oracle; this is not a
  useful test of exact-workload logic and is rejected.
- Changing only `data_cursor_end` is schema-valid and would exercise the cursor
  branch, but it would not test the processed-token oracle that this probe was
  registered to cover.
- Building a second product run with a different inner-step config would test
  argument/config mismatch, not corruption of the durable workload projection,
  and would duplicate the expensive fixture.
- Updating processed and effective tokens together to 15 preserves every table
  CHECK constraint while contradicting the registered workload and the retained
  update/rollup rows. This is the smallest direct counterexample and is chosen.

## Required rewrite and RED evidence

The pre-fix RED evidence is the attempt-3 log: the probe fails at SQLite rather
than producing the required Checker FAIL. The rewrite must:

1. update `processed_tokens_this_cycle` and
   `effective_tokens_this_cycle` together to 15;
2. read the row back and assert `(15, 15)` so future schema changes cannot turn
   the mutation into a no-op;
3. run the aggregate Checker;
4. require status `FAIL`, cleanup ineligible, and the exact cycle-workload error;
5. leave schema enforcement enabled and all product code unchanged.
