## 1. Critical: a selected but unprepared merge batch is permanently unrecoverable after leader failure

**Location**

- `fs_diloco/storage/authority.py:2786` (`try_select_batch`)
- `fs_diloco/storage/authority.py:3302` (`reconcile_publications`)
- `fs_diloco/runtime/services/merge.py` (merge attempt sequence)
- `fs_diloco/runtime/syncer.py:164` (startup reconciliation)

**Problem**

`try_select_batch` atomically creates a `selection_batches` row in `selected`
state and moves every chosen update from `pending` to `selected`. The next step
in `MergeService.merge_once` is `prepare_publication`; if the leader crashes or
raises between those two commands, no recovery path exists:

- `reconcile_publications` only considers `publication_intents` whose state is
  `prepared` and whose `owner_epoch` differs from the current epoch. A batch
  with no intent is invisible to it.
- `try_select_batch` queries only `u.status='pending'`, so the `selected` rows
  are never re-eligible.
- `ingest_proposal` replay does not reset `selected` rows, and no other command
  resets a selected batch unless a retirement/commit conflict happens to touch
  that exact fence.

The same stall occurs on ordinary non-crash failures inside the merge attempt,
e.g. an unhandled `OSError` while loading update vectors after selection.

**Verification**

A one-off authority simulation performed: ingest one proposal, commit genesis,
`try_select_batch`, release the leader, acquire a successor, run
`reconcile_publications`, then retry selection. The retry returned
`batch=None`, `eligible_contributors=0`, and the update remained `selected`.

**Impact**

Global training permanently stalls for that batch; quorum can never be formed
again and the run can only be rescued by retirement/terminal handling or
manual intervention. This is a distributed-system liveness defect.

**Suggested fix**

Add a fenced successor command (or extend `reconcile_publications`) that
reconciles `selection_batches.state='selected' AND owner_epoch<>current_epoch`
by resetting still-current selected updates back to `pending` (preserving the
per-contributor newest-first invariant), and add a crash-matrix test for the
selection-without-prepare prefix.

## 2. `observe_proposal_visibility` and its schema are dead; terminal proposal-visibility grace never records observations

**Location**

- `fs_diloco/storage/authority.py:1398` (`observe_proposal_visibility`)
- `fs_diloco/protocol/authority.py:278` (`VisibilityDecision`)
- `fs_diloco/storage/schema.sql` (`proposal_visibility`,
  `proposal_visibility_archive`)
- `fs_diloco/runtime/services/terminal.py:209` and `:332`

**Problem**

`observe_proposal_visibility` is only referenced by tests and by the authority
surface itself; no runtime caller exists. The terminal service starts a
`proposal_visibility_deadline`, but its polling loop only calls `self.ingest()`
and `_all_declared_final_updates_visible()`, which checks `update_status`
through normal proposal ingestion. It never records missing/malformed/identity
failure observations through `observe_proposal_visibility`, so the entire
stable-failure/terminal-disposition machinery (`proposal_visibility`,
`proposal_visibility_archive`, `VisibilityDecision`, and their tests) is
unreachable in production.

**Impact**

Substantial unused complexity and schema surface; the terminal protocol appears
to provide visibility adjudication that it does not actually perform.

**Suggested fix**

Either wire the visibility decision into `_ingest_proposals`/terminal drain (and
use its terminal dispositions), or delete the API, tables, and tests as
obsolete.

## 3. `data.shuffle_blocks` is ignored by the production data iterator

**Location**

- `fs_diloco/core/config.py:126` (`shuffle_blocks`)
- `fs_diloco/modeling/hf_data.py:134` (`build_indexed_batch_iterator`)
- `fs_diloco/modeling/hf_data.py:99` (`_batched_blocks`, the only shuffle-aware path)

**Problem**

`build_indexed_batch_iterator` always derives block positions from
`IndexedBlockCursor.deterministic_sample_index` and never reads
`config.data.shuffle_blocks`. The shuffle-aware `_batched_blocks` helper is used
only by `tests/test_data_shuffle.py`; production never calls it. Consequently
`shuffle_blocks: false` has no effect.

**Verification**

Generated the first three synthetic batches with `shuffle_blocks=True` and
`shuffle_blocks=False`; the tensors were identical.

**Impact**

The configuration contract is broken and a config field is a false source of
truth. Tests validate a dead helper rather than the production path.

**Suggested fix**

Either honor `shuffle_blocks` in `build_indexed_batch_iterator` (e.g. use the
identity permutation when disabled) or remove the option and its dead tests.

## 4. The documented `fs_diloco.tools.clean_run` CLI does not exist

**Location**

- `website/app/(docs)/user-guide/page.tsx:36,41`
- `website/app/(docs)/reference/page.tsx:194`
- `tools/clean_run.py` (actual implementation lives outside `fs_diloco/tools/`)
- `tools/clean_run.py:526` (`"tool": "fs_diloco.tools.clean_run"`)
- `fs_diloco/tools/__init__.py` (docstring advertises cleanup tools)

**Problem**

The docs and reference pages instruct users to run
`python -m fs_diloco.tools.clean_run`, but `fs_diloco/tools/clean_run.py` does
not exist. Verified directly: importing `fs_diloco.tools.clean_run` raises
`ModuleNotFoundError`. The tool is only runnable as `python tools/clean_run.py`,
and the tests import it through `tools.clean_run`. The tool's own manifest still
claims the nonexistent package path.

**Impact**

Documented operator workflow fails; the package surface and its documentation
disagree. The module-coverage manifest does not catch this because the file is
tracked under `tools/`, not `fs_diloco/tools/`.

**Suggested fix**

Move or re-export the module as `fs_diloco/tools/clean_run.py` and update
`tests/module_coverage.json`, or change every doc/CLI/manifest reference to the
real `tools.clean_run` invocation.

**Suggested fix**

delete the obsolete assertions), and regenerate/update coverage metadata if the
surface mapping changes.

## 6. The designed monotonic lease-safety boundary is not wired into the runtime, and several other production surfaces are dead

**Location**

- `fs_diloco/storage/leader_lease.py:49` (`LeaseSafetyTracker`)
- `fs_diloco/storage/authority.py:754,1000` (`lease_safety_check` hook)
- `fs_diloco/runtime/syncer_entrypoint.py` (authority factory never passes `lease_safety_check`)
- Dead surfaces: `fs_diloco/core/versions.py:13`
  (`LEARNER_HEARTBEAT_FORMAT_VERSION`), `fs_diloco/protocol/selection.py:12`
  (`PersistentFairSelector`), `fs_diloco/observability/logging_utils.py:18`
  (`JsonlLogger`), `fs_diloco/modeling/hf_data.py:32` (`synthetic_batches`),
  and several tensor-codec writers used only by tests.

**Problem**

`LeaseSafetyTracker` is implemented and unit-tested but never instantiated or
passed to `LeaderAuthority` by the syncer runtime. `LeaderAuthority._verify_token`
therefore relies only on wall-clock lease expiry. The intended monotonic safety
boundary (protecting against wall-clock stalls/freezes during long business
operations) is not enforced. The other listed classes/constants have no
production callers and exist only for tests.

**Impact**

The distributed safety design is incomplete as implemented, and the repository
retains obsolete surfaces that contradict the “delete obsolete code” project
rule.

**Suggested fix**

Wire the tracker into the renewer/business path (`mark_renewed` on each
successful renewal, `assert_safe` before fenced commands) or remove it; remove
or fold the unused constants, helpers, and their test-only coverage.

## Additional minor observation

`wait_for_current_latest` raises `StopIteration(current.terminal)` when a
terminal control is already visible (`fs_diloco/storage/control.py:258`), and
the learner startup call at `fs_diloco/runtime/learner.py:194` does not handle
it. A learner admitted or restarted after terminal will therefore exit with a
`StopIteration` traceback instead of a clean terminal exit. This is lower
priority because normal admission is closed before terminal, but it is an
uncovered control-flow gap.

## Summary

The strongest finding is the unrecoverable selected-batch state (1), which
should be fixed and crash-tested before relying on failover. Findings 2-4 are
dead or contradictory surfaces that should be either wired/removed, and 5 keeps
the suite red. Finding 6 shows the monotonic lease-safety design is not
actually enforced.
