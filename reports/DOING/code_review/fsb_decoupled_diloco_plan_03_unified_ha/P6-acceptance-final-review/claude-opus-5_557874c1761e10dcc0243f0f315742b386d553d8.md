## 3. Things checked that are correct

**H1 remediation in `_audit_history_records` (`fs_diloco/storage/authority.py:5695-5751`) is correct
and complete for the reported failure:**

- The protection predicate is exactly the ack's precondition. `acknowledge_terminal_contributor`
  (`authority.py:4520-4545`) first requires `contributor_progress.last_cycle_seq == final_cycle_seq`
  and only then looks up `cycle_receipts WHERE stable_contributor_key=? AND cycle_seq=?`. The row it
  needs is therefore always the row named by `contributor_progress.last_receipt_id`, which is what the
  new `NOT EXISTS`/anti-join clauses retain.
- `contributor_progress.last_receipt_id` is written in the same statement as `last_cycle_seq`
  (`authority.py:1322-1345`), so `last_receipt_id` always denotes cycle `last_cycle_seq`. The
  independent `receipt_only` query (`authority.py:5765-5776`) is bounded by
  `r.cycle_seq < p.last_cycle_seq`, so it can never re-admit the protected receipt through the back
  door. `token_fates`, `proposal_observations` and `proposal_conflicts` are all derived from
  `receipt_ids`, so the closure holds.
- The `LEFT JOIN contributor_progress AS p ON ?=1 AND p.last_receipt_id=u.cycle_receipt_id WHERE
  p.stable_contributor_key IS NULL` construction is a correct parameterized anti-join in SQLite: with
  `?=0` the ON clause is false, `p.*` is NULL, and every update passes, restoring the terminal
  behaviour exactly.
- The terminal ordering is right: `fs_diloco/runtime/syncer_v4.py:285-287` calls
  `terminal_service.finalize()` — which sets `controller_state.state` to `finalized`/`error`
  (`authority.py:4705-4732`, via `terminal.py:206-211`) — **before** `maintenance_service.tick(force=True)`.
  The force pass therefore observes `protect_current_receipts = 0` and can still produce the
  current-only hot authority that `plan03_p6_validate_run.py:243-244` requires. A crash between the
  two is recoverable: a successor re-enters the same branch, skips the already-finalized transition
  (`terminal.py:206`), and re-runs the force tick.
- Protection release at `error` is safe: both `finalize_terminal` branches require
  `awaiting_ack == 0` and zero outstanding tokens (`authority.py:4686-4698`), so no acknowledgement
  can follow.
- No FK is violated by deferring these deletions to the terminal pass:
  `terminal_contributor_fences.final_update_id` (`schema_v4.sql:90-105`) has no `REFERENCES` clause,
  and `acknowledge_terminal_contributor` tolerates an already-archived update row
  (`authority.py:4557-4565`, `if update is not None and (...)`). `delete_order`
  (`authority.py:3826-3838`) still removes children before parents.
- `_require_visibility_receipt` (`authority.py:4768-4790`) is likewise satisfied while protection is
  on; its only caller `observe_proposal_visibility` (`authority.py:1610-1928`) has no production
  runtime call site, so it is not a live exposure either way.
- The new regression `tests/storage/test_authority_p3_operational.py:1301-1391` is a genuine RED: with
  two contributors and quorum-one interleaving, `safe_cutoff = min(1, 2-1) = 1`, so learner-0's
  cycle-1 receipt — still its progress anchor — was inside the pre-fix archive set. The test asserts
  both halves (retained while open, eligible after `finalized`) and that both acks return `"acked"`.
  `failures.md:1131-1133` records the corresponding compute-node RED (job `2514056`, focused
  `626 passed, 1 failed`).
- Bounded-hot-authority is preserved: `stable_contributor_key` is `learner_id` (static) or
  `str(stream_id)` (dynamic, `fs_diloco/protocol/contributor.py:96-98`), so `contributor_progress` is
  bounded by `num_learners` / `stream_pool_size` and the pinned closure is bounded with it.
