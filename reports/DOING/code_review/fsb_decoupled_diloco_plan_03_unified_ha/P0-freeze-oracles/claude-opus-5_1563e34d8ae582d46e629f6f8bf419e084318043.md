#### H-1（correctness / 验收条件）`P0-ORACLE` 的「bitwise 等价」几乎是恒真式，无法承担 P2/P3 语义归因锚点的职责

**证据**：`tests/reference/test_plan03_classic_static_oracle.py:70-145`

`_semantic_projection()` 对 classic 和 HA 两条臂调用的是**同一份纯函数**、并且喂给它们的是**同一个 `tape` 对象**：

```
:97-101   vector_by_id = {metadata["update_id"]: vector for metadata, vector in tape.proposals}
          merged = weighted_average_tensors([vector_by_id[row["update_id"]] ...], ...)
:102-108  state0 = init_outer_state(tape.theta_v0, tape.outer)
          theta_v1, state1 = outer_optimizer_step(tape.theta_v0, tape.theta_v0 - merged, state0, tape.outer)
```

因此 projection 中的 `merged` / `theta` / `outer_step` / `outer_momentum` **完全由 tape 决定，与 store 无关**，两臂必然逐位相同；`torch.equal` 断言（`:185-186`）无论 store 行为如何都会通过。

更进一步，`selected_order` 也不敏感：`select_one_per_learner` 在 `fs_diloco/protocol/merge.py:83` 无条件执行 `selected.sort(key=lambda row: (row["learner_id"], int(row["local_step_end"])))`，把输出规范化成按 `learner_id` 排序，因此即使两个 store 的 `eligible_updates` 返回顺序不同，`selected_ids` / `selected_order` 仍相同。

`predecessor_version`（`:144`）是 `int(committed["version"]) - 1` **算术推导**出来的，不是从 DB 读的（`global_versions` 表本身没有 predecessor 列，`fs_diloco/storage/schema.sql:7-18`）。计划 §5.1.6 与矩阵 `P0-ORACLE` 的 test_contract 明确要求比较「version predecessor」，当前实现对该字段是空断言。

**实际被这条测试覆盖的 store 行为只有三点**：(a) 两个 store 的 `eligible_updates` 都返回 2 行；(b) `base_global_version` / `tokens_this_update` 往返持久化正确（经 `normalized_update_weights`，`merge.py:16-33`）；(c) commit 返回 `version == 1`。

**失败场景**：P2/P3 修改 selection 或 commit 语义后，用这组 golden fixture 做归因时，任何只影响 merge 数学、outer state 或 predecessor 链的回归都不会被检出——因为这些值根本不经过被测协议路径。`classic_full_v1_trace.json` 与 `static_ha_v1_trace.json` 两个文件的 `semantic_projection` 目前逐字节相同，冻结的是一组与协议无关的常量。

**修复建议**：
1. 让 `theta` / `merged` / `outer state` 经由**每条臂各自的 store 往返**产生（例如把 v0 theta、merge 结果的 checkpoint path/size/sha256 写入各自 store，再从 store 读回驱动 outer step），或者至少把两臂的 merge 输入改为**从各自 store 读回的行**而不是共享的 `tape.proposals`。
2. `predecessor_version` 改为从 store 查询（HA：`global_versions` 的 committed 前驱 / publication 记录；classic：`max(version) where status='committed'` 在 commit 前采样），而不是 `version - 1`。
3. 在 tape 中引入至少一个**能区分两个 store 的**输入（例如乱序 `committed_at` 到达、`base_global_version` 不同的 staleness），使 `eligible_updates` 的排序/过滤真正参与 projection。
4. `static_ha_v1_trace.json` 目前只被 `classic_fixture == ha_fixture`（`:196`）间接校验；应把 HA projection 也独立序列化后与该 fixture 比对（`:202-213` 只用了 `classic_projection`）。

**缺失测试**：
- 一个 negative 测试：人为篡改 golden fixture 中的 `theta_float32_le_hex` 或 `weights`，断言 oracle 测试会失败（当前无法保证）。
- 乱序到达 / staleness 非零 / `quorum_max == N` 边界的第二组 tape。

#### H-4（并发/持久化不变量）冻结的 INIT-01 fallback 漏掉了 `mkdir(final)` 与 `.identity` 写入之间的 crash 窗口，且该窗口下的 retry 会抛未处理的 `FileNotFoundError`

**证据**：`scripts/miyabi/plan03_fs_capability.py:117-151`

```
:125-131  try:
              final.mkdir()
              _write_exclusive(final / ".identity", identity)
              _fsync_dir(final); _fsync_dir(final.parent)
          except FileExistsError:
              if (final / ".identity").read_bytes() != identity:
                  raise RuntimeError("final reservation identity collision")
```

若进程在 `final.mkdir()` 成功之后、`.identity` 写入完成之前崩溃（这在 shared FS 上是完全可达的物理状态），retry 时 `final.mkdir()` 抛 `FileExistsError`，随后 `(final / ".identity").read_bytes()` 抛 **`FileNotFoundError`**——既不是 `RuntimeError("final reservation identity collision")`，也不是成功恢复。

crash-prefix 枚举（`:180-197`，`for prefix in range(4)` 配 `link_limit=prefix`）**最早的 prefix=0 也是在 reservation 全部完成之后才"崩溃"**，因此这个窗口根本没有被 probe 覆盖。冻结 artifact `20260808-225600_p0-shared-fs-capability_pass.json` 却记录 `"same_identity_retry": true`，计划 §5.1.11 与 §7 的 `INIT-01` 也据此写成「同 identity retry 可完成」。

次生问题：
- `.identity` 写入前没有 `_fsync_dir(final.parent)`，crash 后 `final` 目录项本身可能未持久化（probe 里 `_fsync_dir(final.parent)` 在 `:129` 才执行）。
- 若 `final` 是一个**文件**而非目录，`mkdir` 抛 `FileExistsError` 后 `read_bytes()` 会抛 `NotADirectoryError`，同样落在未处理路径。

**失败场景**：P3 按冻结契约实现 initializer 后，一次恰好落在 reservation 窗口的 crash 会让后续所有 retry 永久抛 `FileNotFoundError`，run 既无法完成也无法被别的 identity 安全接管——即 `INIT-01`「同 identity retry 可完成 / 异 identity fail closed」两条都不成立。

**修复建议**：
1. 把 reservation 拆成可判定的三态：`final` 不存在 → 全新预留；`final` 存在但无 `.identity` → **同一 identity 允许补写 `.identity` 完成预留**（因为无 `.complete` 时 reader 视为不存在），并显式定义此路径；`final` 存在且 `.identity` 不匹配 → fail closed。
2. 显式捕获 `FileNotFoundError` / `NotADirectoryError` 并转成明确的 `RuntimeError`，禁止裸传播。
3. probe 的 crash-prefix 枚举扩展到 reservation 内部（至少 `mkdir` 后、`.identity` 后、`fsync` 后三个点），并把 `_probe_directory_publish_fallback` 的 `link_limit` 语义改成统一的 step 索引。
4. 同步更新计划 §5.1.11、§7 `INIT-01` 与矩阵 `INIT-01` 的措辞（当前只枚举了 object-link/fsync/marker 三类 crash point）。

**缺失测试**：
- `plan03_fs_capability.py` 无任何单元测试。需要一组不依赖真实 shared FS 的 `tmp_path` 测试，逐 crash prefix（含 reservation 内部）断言：marker 前不可见、同 identity retry 完成、异 identity fail closed、已完成 root 不可覆盖。这组测试应该常驻 `tests/`，而不是只存在于一次性 probe 脚本里。

#### M-5（并发 / 回归风险）`_run_processes` 顺序 `communicate()` 存在管道死锁风险

**证据**：`scripts/miyabi/plan03_p0_performance.py:62-86`

三个子进程都用 `stdout=PIPE, stderr=STDOUT`，但读取是**串行**的：先 `communicate()` 读 syncer 直到 EOF，再读 learner_000、learner_001。若某个 learner 在 syncer 退出前写满 64KiB 管道缓冲区，它会阻塞在 write 上；syncer 若在等这个 learner 的 proposal，则相互等待直到 90s 超时。

当前 tiny workload 输出很小所以没触发。但同一 runner 被冻结为 G10 的方法实现，正式 workload 的日志量必然超过管道缓冲区。

另外 `finally`（`:90-99`）在 `kill()` 之后没有再次 `wait()`/`communicate()`，会留下僵尸进程和未关闭的管道 fd。

**修复建议**：改为并发消费——用 `threading` 分别 drain 每个进程的 stdout，或把各进程 stdout 重定向到 scratch 内的文件再读取 tail；`kill()` 后补 `process.wait()`。

**缺失测试**：用一个故意输出 >1MiB 的 fake 子进程验证 runner 不会死锁。
