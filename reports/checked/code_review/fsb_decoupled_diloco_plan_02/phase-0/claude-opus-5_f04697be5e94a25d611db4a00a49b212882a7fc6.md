## 3. Findings

### High

#### H1 — FEAS-04 被标记 `complete`，但 `finished`（及 `queued`）状态从未对真实 scheduler 取证；探针把"查询成功但记录为空"与"状态未知"混为一谈

**证据**

- `plan02_pbs_capability.py:84-97`：`fields = parse_qstat_full(stdout) if returncode == 0 else None`。`qstat -H -f` 在子作业仍在运行时返回 `rc=0` 且空输出 → `fields = {}` → `classify_scheduler_state({})` 走到 `state=""`，落到 `plan02_pbs_capability.py:59` 的 `return "unknown"`。
- `plan02_pbs_capability.py:155-170`：`_wait_for_child` 一旦看到子作业 artifact 就 `break`，随即在同一时刻发起 `historical=True` 查询——此时子作业必然尚未进入 history，因此 `finished` **在构造上不可能被观测到**。
- F11/F12：011200、011500、011600 三次运行的 `historical_query` 全部是 `{"classification":"unknown","fields":{},"returncode":0}`；真实观测到的分类只有 `prologue` 与 `running`。
- 本次只读复查证明能力本身存在：同样两个作业现在返回 `job_state=F`、`substate=92`、`Exit_status=0`、`run_count=1`（array 另有 `Rerunable=True`、`array_indices_submitted=0-1`）。
- Checker 端唯一相关断言是 `check_plan02_feasibility.py:115` 的 `state_classifier_validated is True`，而该布尔来自 `plan02_pbs_capability.py:184-198` 用**硬编码字典**做的自检（`{"job_state":"Q","substate":"10"}` 等），与真实 scheduler 输出无关。
- requirement matrix 第 5 行 FEAS-04 的冻结 `test_contract` 明确要求 "queued prologue running finished unknown 状态"，而计划 §13 规定"占位值 `TBD` 或证据缺失时不得标记 complete"。该行已被置为 `complete`。

**影响**

1. 与冻结的 requirement contract 不一致：`complete` 声明超出实际证据。
2. Phase 1/2 的 recovery reconciliation、claim 超时判定、以及计划 §14 中"PBS `Exit_status=0` 但无真实 workload 输出"这一立即 `BLOCKED` 条件，都依赖终态查询；当前实现在终态查询上会静默返回 `unknown`，无法把"作业已结束、退出码 0"与"scheduler 不可查"区分开。这正是 stale-job 判定最危险的一类混淆。
3. `queued` 亦无真实样本，无法证明排队作业不会被误判。

**具体修复**

- 在 `_query_job` 中区分三态：`rc != 0` → `query_failed`；`rc == 0 and not fields` → `no_record`（显式字段，不得复用 `unknown`）；否则按 `job_state` 分类。把该三态写入 artifact。
- 在 `_wait_for_child` 之后新增终态轮询：子作业 artifact 出现后继续用 `qstat -f`/`qstat -H -f` 轮询直到 `job_state=F`（或超时），记录 `terminal_state_observed`、`exit_status`、`run_count`、`substate`，并新增顶层布尔 `terminal_state_query_supported`。
- 记录首次 `qstat` 观测（qsub 返回后立即查询，而非等 1 s），以取得真实 `queued` 样本；若队列即刻起跑而无法取到 `Q`，则显式记录 `queued_observed=false` 并说明。
- `check_plan02_feasibility.py` 的 FEAS-04 分支增加：`observed_states ⊇ {"prologue","running","finished"}`、`terminal_state_query_supported is True`；若终态不可查，则必须显式把 `automatic_submission_supported` 与自动 recovery 能力判为不可用（而不是 PASS）。
- 在证据补齐前，requirement matrix 的 FEAS-04 行不应保持 `complete`（或将 `test_contract` 的差异在 matrix/progress 中显式记录为 deferred，并写明负责人与时限）。

**缺失测试**

- `test_query_job_distinguishes_empty_record_from_unknown_state`：伪造 `rc=0/空输出`、`rc!=0`、`rc=0/有 job_state` 三种 `subprocess` 结果，断言三种不同分类。
- `test_classify_scheduler_state_rejects_empty_field_map`：`classify_scheduler_state({})` 不得返回与真实 `unknown`（如 `job_state=Z`）相同的值。
- `test_checker_blocks_when_terminal_state_never_observed`：FEAS-04 证据缺少 `finished` 观测时 Checker 必须 `BLOCKED`。

#### M4 — 任一探针/聚合阶段失败时不会产生任何 `_blocked.json`，与 §5.6 的 Checker artifact 契约不符

## 4. Correctness / 回归 / 错误处理 / 并发与持久化不变量评估

**正确性与回归风险**：范围内不含 `fs_diloco/` 生产代码，Phase 0 对现有训练路径无回归面。唯一被修改的既有文件 `scripts/miyabi/sqlite_shared_fs_probe.py` 保持了 `stress`/`verify`/`kill-reopen` 子命令的原有行为；`_configure_connection()` 新增的 5 s 启动 busy timeout（`:26-33`）只放宽了启动期等待，随后仍降回配置值，既有测试 `test_sqlite_stress_probe_and_kill_reopen` 未受影响并通过。

**错误处理**：探针普遍 fail-closed——`plan02_fault_probe.py` 在每个关键判据处 `raise`，`plan02_source_gate.py:148-158` 用 `except BaseException` 写出 `BLOCKED` 并以 `exit 3` 结束，`check_plan02_feasibility.py:165-171` 在解析异常时把全部 requirement 置 `BLOCKED`。主要缺口是 M4（作业级失败无结构化 artifact）与 M1/M2/M3（Checker 侧的 fail-open 与恒真断言）。`check_plan02_feasibility.py` 捕获 `BaseException` 也会吞掉 `KeyboardInterrupt`，属可接受的取舍。

**并发不变量**：writer-lock 探针的时序是正确的——`child.wait()`（`:178`）在 successor 连接之前完成，确保 `SIGKILL` 后文件锁已释放；`_wait_for` 基于 `time.monotonic()` 且都带超时；`old-cache-writer` 用 `/proc` 的 `T` 状态而非 sleep 做同步（`:329-334`）。contention 循环把每次 `sequence` 的等待从 `transaction_started` 起算并包含全部重试（`sqlite_shared_fs_probe.py:224-243`），`PRIMARY KEY(writer_id, sequence)` 保证重试不会重复计数；非 busy/locked 的 `OperationalError` 一律上抛（`:277-278`），不会把 I/O 错误吞成"争抢"。

**持久化不变量**：所有 artifact 写入都是 `mkstemp` + `fsync` + `os.replace` 的原子发布（4 个脚本中各自实现）。跨节点交叉校验是本次证据里最有力的部分：`plan02_phase0_aggregate.py:83-100` 用只读连接直接从 DB 统计 `event_count`/`distinct_writer`，与各 writer 自报的 `requested/committed` 做三向相等校验（400/400/400、8 个 distinct writer），这不是探针的自述。`journal_mode=DELETE` + `synchronous=FULL` 在共享 FS 上跨两节点、8 进程、1198 次 busy 重试后 `integrity_check=ok`，构成对该共享文件系统 POSIX advisory locking 可用性的有效证据。

**值得 Phase 1 注意的量化结果（非缺陷）**：单行 lease 在 8 进程争抢下 `maximum_writer_wait_seconds=2.6155`（attempt 3 曾达 4.006），而计划 §6.1 的 `lease_busy_timeout_ms` 起点为 5000 ms。真实 HA 拓扑中 candidate 应只读观察、不周期性争抢 writer lock，但该分布说明 5 s 上限的裕度有限，建议在 P1-L1 用真实 candidate 行为重测后再冻结。

**测试覆盖**：新增 8 个用例（`tests/test_plan02_feasibility.py`）+ 2 个用例（`tests/test_sqlite_probe.py`），本次复跑 `10 passed in 4.04s`。覆盖到位的部分：三个 fault 探针的端到端行为、PBS ID 规范化与 `qstat -f` 续行解析、Checker 的 stdout 双值契约与一条 fail-closed 路径、两条针对历史失败的回归断言、跨进程 SQLite 争抢与启动期锁等待。缺口见 H1、M1–M4、M6 的"缺失测试"小节；此外 Checker 的 fail-closed 只测了一个字段（`counterexample_reproduced=False`），未覆盖整节缺失、空集合、以及 FEAS-01/03/04/05 的拦截路径。

## 6. Inferences（推断）

- I1. 由 F2/F3/F4 可推断：最终证据是在 review-target 的**完全相同源码内容**上产生的（尽管 commit 记录的是 base commit + dirty），因此本次 artifact 与被审代码之间不存在源码漂移。这是本次实施在证据链上做得最扎实的一点。
- I2. 由 F12 与本次只读复查可推断：`finished` 状态缺失是**探针时序缺陷**，不是 Miyabi 的 scheduler 能力限制。修复成本很低（在子作业终止后再查一次 history），但在修复前不应把 FEAS-04 的终态识别能力视为已冻结。
- I3. 由 §2.3 变异表可推断：当前 Checker 的判别力主要来自探针内部的 `raise`，而非 Checker 自身。这在 Phase 0 由同一份代码端到端执行时尚可接受；一旦 Phase 1/2 的 Checker 需要复核他人产出的证据或历史 artifact，该结构会不足。M1–M3 的修复应在 Phase 1 Checker 开工前完成，以免把同一模式复制到更大的 checker 上。
- I4. 由 F9 的等待分布推断：跨节点单行 lease 的写锁等待在中等争抢下已达秒级；Phase 1 的 `lease_busy_timeout_ms=5000` 与 `renew p99 < lease_duration/4` 门槛需要用真实 candidate 行为（只读观察 + 疑似过期才争抢）重测，不能直接沿用本次 8 进程全争抢的数据作为正式默认。
- I5. 由 F14 推断：两次失败的根因分析与回归断言质量较高（attempt 1 的破坏性路径已被"不接受继承变量 + resolve 前缀校验 + 回归测试"三重收敛）。三次失败升级阈值未被触发，`code_review.md` 保持为空占位是正确的。
- I6. 由 M5 推断：`-r y` 是 Miyabi 上使用 job array 的硬性前提，因而 Phase 2 的 learner 编排将默认运行在 rerunable 作业上。若 Phase 2 的 launch outbox 以 PBS job ID 作为幂等键，scheduler 自动 rerun 会破坏"每 logical request 至多一个 admission"的不变量。这应在 Phase 2 设计冻结前解决，而非在 P2-L4 才发现。

## 8. 最终决定

**CHANGES_REQUIRED**

理由：Phase 0 的实施质量整体较高——不触碰生产代码、证据链可复核（源码指纹与被审 commit 逐字节一致）、Checker 结论可复现、跨节点 SQLite 与固定 cache 反例证据充分、两次失败的根因与回归覆盖到位。但存在一项 High finding：FEAS-04 已在冻结的 requirement matrix 中被标为 `complete`，而其 `test_contract` 要求的 `finished`（及 `queued`）状态从未对真实 scheduler 取证，且探针把"查询成功但无记录"与"状态未知"混为一谈——我已只读验证该能力在集群上确实存在，缺失属探针时序缺陷。按 `plans/AGENTS.md` 的处置规则，High findings 阻止阶段完成。另有 6 项 Medium（Checker 的空集合 fail-open、常量布尔断言、争抢/starvation 判据不可证伪、阶段性失败不产出 BLOCKED artifact、rerunable 语义未记录、aggregate/source-gate 无单元测试）需修复或带证据延期。

在 H1 与上述 Medium 处置完成、并按 §7 第 1 条重取 Phase 0 证据后，本阶段可以通过。
