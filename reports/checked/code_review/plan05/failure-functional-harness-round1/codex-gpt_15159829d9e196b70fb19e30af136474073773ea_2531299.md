## 结论

三次 functional 尝试均在有效 Miyabi compute allocation 上执行。第一次发现 proposal ingestion 的跨 stream 饥饿；第二次在公平 ingest 后发现 proposal backpressure、functional terminal 配置和 co-allocated scheduler oracle 不一致；第三次已经证明这些修复有效：run 精确结束在 global version 4，receipt/proposal 为 15/15，ledger balance 为 0，所有 4 个 instance graceful terminal，单一 PBS job 覆盖 5 个预期 host。

第三次唯一失败原因是 Checker 把 `quorum_max` 错当成每个 global version 必须选择的固定数量。生产 selection transaction 明确在 eligible proposal 达到 `quorum_min` 时提交，并最多截取 `quorum_max`；functional config 为 3–4，因此每版 3 个 proposal 是合法且实际发生的结果。authority 的 12 个 selection credit、4 个 version 各 960 direct token、12 个 applied proposal 和 terminal/rollup 的 3840 direct token 完全一致。

第四次尝试前只应修改 Checker：每个 committed version 的 applied count 必须在 `[quorum_min, quorum_max]`；selection credit 总数必须等于 applied proposal 数；expected direct token 必须从 durable applied proposal workload 推导，并逐版与 `global_versions.direct_weight_tokens_applied` 比较。receipt/proposal 一一对应、applied-or-dropped fate、terminal exact version、ledger balance、topology 和 fence oracle保持不变。

## 输入、状态、持久化与恢复链路

1. `configs/full_protocol_functional.yaml` 注册 4-stream pool、`quorum_min=3`、`quorum_max=4`、20 inner step 和 4 outer version。`max_terminal_merges=0` 后，terminal final version 精确为 4。
2. 四个 learner 通过 bootstrap admission 获得唯一 fence。修复后的 Syncer 先 durable ingest receipt 和 proposal，再发布 receipt ack；第三次 evidence 中 receipt 与 proposal 均为 15，说明 backpressure 和一一对应成立。
3. `_ingest_proposals` 优先尚未进入 pending set 的 current stream；`try_select_batch` 从每个 contributor 取最新 pending proposal，在 valid row 数量至少为 3 时选择 `valid_rows[:4]`。它没有等待第 4 个 proposal 的契约。
4. 第三次运行每次 merge 到达 3 个 eligible row 即提交。4 个 version 共应用 12 个 proposal；persistent selection credit 总和为 12。贡献者 0/1/2 各应用 4 次，贡献者 3 为 0，属于小样本调度时序结果，不违反每 batch 唯一 contributor 或 quorum。
5. `commit_merge` 从 selection batch 的实际 `selected_rows` 求和 `effective_tokens_this_update`，每版记录 960 direct token；terminal state、global-version history 和 token rollup 均记录 3840。15 个 receipt 中另有 3 个 proposal durable dropped，960 token 已正确进入 `direct_dropped`，总 ledger balance 为 0。
6. Checker 当前以 `expected_global_steps * quorum_max` 计算 selection credit、applied proposal 和 direct token，得到 16/5120。这与 authority 的 variable-quorum contract 冲突，且会使同为 quorum 4–8 的正式配置把合法 4-way merge误判为失败。
7. PBS job、5-node actor attestation、source identity、SQLite integrity、terminal ownership release、bootstrap launch rows和 cleanup projection均通过。第三次失败与节点、MPI、lease、recovery、文件可见性或 scheduler 生命周期无关。

## 备选解释与决策

- 把 functional config 改成 `quorum_min=quorum_max=4`：拒绝。该配置还用于 learner-loss/replacement functional oracle；强制 4 会消除故障窗口内由 3 个 surviving contributor 前进的当前设计。
- 修改 Syncer，在达到 `quorum_min` 后继续等待 `quorum_max`：拒绝。authority 和 config 已明确把两者定义为下界与上界；额外等待会改变 runtime 语义，并可能在 failure/no-replacement 场景永久阻塞。
- 仅删除 direct-token 断言：拒绝。必须保留逐版 publication、applied proposal、terminal 和 rollup 的交叉核对，只把错误的固定数量改成 durable actual quantity。
- 接受任意非零 batch：拒绝。每个 version 仍必须在 `[quorum_min, quorum_max]`，每个 batch 只能包含一个 current proposal per contributor，selection credit 必须等于 applied row 数。
- 因 stream 3 在本次 4 个 version 中未被应用而判失败：拒绝。persistent fair credit只对已 eligible contributor排序；短运行不保证每个 stream 已及时产生 pending proposal。正式质量比较可以报告 per-stream service，但不能把 `quorum_max` 伪装成公平性下界。

## RED 与通过条件

修复后必须满足：

1. synthetic Checker fixture 显式构造 `quorum_min < quorum_max` 且每版只应用 `quorum_min` 个 proposal，仍应 PASS。
2. 任一 version 少于 `quorum_min` 或多于 `quorum_max`、selection credit 与 applied rows 不等、version direct token 与所选 proposal 不等、terminal/rollup direct token 不等时仍应 FAIL。
3. no-failure functional evidence 继续要求 receipt/proposal 一一对应、所有 update 为 applied 或 dropped、direct fate精确、terminal version 为 4、ledger balance 为 0、5-host co-allocated topology 与 1 个 scheduler job一致。
4. syncer-takeover 继续要求 primary exact boundary、lease expiry/supersession、successor publication 和无 stale-epoch commit。
5. 修复后的 clean target 必须先通过完整 U1，再运行 fresh functional roots。

## Findings

### F1 — High — Checker 把 `quorum_max` 当作固定 batch size

- 证据：`try_select_batch` 在 `len(valid_rows) >= quorum_min` 后选择 `valid_rows[:quorum_max]`；第三次每版 3 个 selected row，满足 3–4 配置。Checker 却对 selection credit、applied count 和 direct token使用 `steps * quorum_max`。
- 处置：`fixed`；所有计数改为逐版区间约束和 durable actual applied rows交叉核对。

### F2 — Medium — 现有 Checker fixture 未覆盖 variable quorum

- 证据：fixture 把 stream pool 和 quorum 都缩为 1，无法区分“合法下界 batch”和“错误固定上界公式”。
- 处置：`fixed`；扩展现有 harness owner，以至少一个 3–4 或 1–2 current fixture覆盖 variable-quorum PASS，并保留超界负例。

Verdict: CHANGES_REQUIRED
