## 输入、状态、持久化与恢复链路

1. `init_run` 从唯一 resolved config 生成 descriptor、`.identity`、authority SQLite 和 bootstrap marker，再通过 create-once manifest 发布 run root。`.identity` 的 checksum 能证明内容未被未检测地改变，但当前 validator 接受任意额外字段，因此重新计算 checksum 后的旧 `mode` 仍会进入 completed-run 恢复路径。这违反“不读取旧 run root”的严格当前格式要求。
2. `initialize_authority` 接收 `MembershipScope`，但第三次 target 只把 run/source/config 写入 `run_identity`。`LeaderAuthority` 和 `AuthorityReader` reopen 时虽接收 scope，却没有任何 durable scope 值可比较；传入 `MembershipScope(2)` 可以打开按 `MembershipScope(1)` 创建的 authority。config hash 间接包含 pool size，但直接 API 没有确认调用者提供的 scope 与该 config identity 一致。
3. leader 首次执行 `initialize_membership` 才根据进程内 scope 创建 streams。若 reopen 调用者在此之前提供错误 scope，authority 没有持久化反证；若之后提供错误 scope，现有 stream count 检查也只在再次执行 command 时触发，不能满足 open-time identity boundary。
4. receipt producer 已使用稳定 `stream_id` 生成 `receipt-0-1.json`，并用完整 canonical fence hash 隔离 instance incarnation。失败测试仍要求已删除的 `receipt-learner-0-1.json`；产品 namespace 与 replacement 隔离均正确。
5. summary collector 对输入目录递归发现 completed layouts，并按完整 run path 排序。fixture 的 Full Protocol run 位于 `full_protocol/`，baseline 位于 `torch_ddp_baselines/`，因此固定顺序是 Full Protocol 后 baseline；测试只改了 run ID，没有同步目录排序事实。去重和原子输出均未失败。
6. 三次 PBS allocation、Python 环境、JUnit 解析和结构化 FAIL artifact 都正常。第三次 Ruff、focused suite 与 SQLite/filesystem fixture 已完整执行，故障与节点、进程生命周期、PBS 排队、网络和 cleanup 无关。

## 备选解释与决策

- 仅依赖 `resolved_config_sha256` 间接绑定 pool size：拒绝。authority API 仍允许传入与 durable config identity 不一致的 scope，错误只会延迟到后续状态转换。
- 仅在 streams 已创建后按 row count 校验 scope：拒绝。fresh authority 在 membership initialization 前仍存在可见的错误 reopen 窗口，且 row count 不是 immutable run identity。
- 保留 generic `write_run_identity(dict)`，只在 reader 侧加字段集合：拒绝。唯一 producer 没有理由继续接受任意 shape；显式参数接口更短，也让旧字段无法被写出。
- 恢复旧 `learner-` receipt ID：拒绝。稳定 contributor key 已唯一收敛为 `stream_id`，恢复旧前缀会重新引入已删除的命名语义。
- 为满足 summary 测试而改为按 run ID 重排 CSV：拒绝。本 plan 没有改变聚合排序契约，现有完整路径排序稳定且不依赖不同 layout 的 run ID；应修正迁移测试。

## RED 与通过条件

修复后必须在 fresh compute allocation 上运行不变的完整 U1 ladder，并满足：

1. legacy `.identity` 字段即使 checksum 与 complete manifest 都重新计算，也必须以 `run identity schema is invalid` 拒绝；staged recovery 同样不得发布旧 identity。
2. 同一 authority 使用不同 `MembershipScope` 的 writable 和 query-only reopen 都必须在 open 时以 `membership scope` 拒绝；正确 scope 的 integrity 与 marker 校验保持通过。
3. receipt replacement 测试继续证明两个完整 fence namespace 不同，并只接受当前 `receipt-0-1.json` ID。
4. summary 两次递归聚合仍分别返回 `(2, 0, 2)` 与 `(0, 2, 2)`，且输出保持按实际 discovered path 的确定顺序。
5. Ruff format/lint、focused pytest、full pytest、website lint/test 必须全部通过；任一步骤失败都不得进入 PREFORMAL。

## Findings

### F1 — High — Run identity 接受 checksum 正确的旧字段

- 证据：`validate_identity_file` 只删除 `identity_sha256` 后复算 digest，不校验精确字段集合。
- 处置：`fixed`；改为唯一显式 producer 和 exact-shape validator，staged/completed 两条恢复路径共同使用。

### F2 — High — Membership scope 未进入 durable authority identity

- 证据：`initialize_authority` 接收 scope，但 `run_identity`、bootstrap marker 和 `_validate_open` 均未记录或比较 pool size。
- 处置：`fixed`；把 `stream_pool_size` 写入唯一 `run_identity` 和 marker，并在所有 open 路径比较。

### F3 — Medium — Receipt test 仍断言已删除的 contributor 名称

- 证据：产品路径为 `updates/receipts/0/<fence-hash>/receipt-0-1.json`，测试仍要求 `receipt-learner-0-1.json`。
- 处置：`fixed`；只更新当前 stream-key 断言。

### F4 — Low — Summary 迁移测试的顺序期望与 fixture layout 不一致

- 证据：`full_protocol/` 在 `torch_ddp_baselines/` 前；collector 按完整 path 排序，实际结果稳定为 Full Protocol 后 baseline。
- 处置：`fixed`；保留产品排序并修正测试。
