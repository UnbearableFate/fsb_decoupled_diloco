## Findings

### PF-01 — Critical — fixed-capacity fault 场景必然在 summary 阶段失败

- `scenario_supervisor._final_authority_evidence()` 明确接受 7 个 `acked` 加 1 个 `hard_crash` terminal fence（`scenario_supervisor.py:429-434`），随后无条件调用 `tools/summarize_runs.py`（`scenario_supervisor.py:705-706`）。
- summary 的 `_terminal_fences()` 却拒绝任何非 `acked` fence，并要求 `final_cycle_seq >= 1`。因此 `failure_no_replacement` 即使产品和 authority 完全满足预注册 oracle，也不能发布 PASS artifact。
- 处置要求：summary 的当前 Full Protocol 投影必须接受注册的 bounded hard-crash terminal state，并从 durable contributor progress/receipt history 推导已完成步数；健康和 replacement 场景仍严格要求 ack。增加真实 current-schema hard-crash summary regression。

### PF-02 — High — formal PASS 未验证 token ledger 与 receipt/proposal fate

- `_final_authority_evidence()` 读取 terminal、updates、launch、instances、epochs 和 versions，但不读取 `cycle_receipts`、`token_fates` 或 `token_rollups`（`scenario_supervisor.py:351-401`）。
- 它只核对每版 4 个 200-step applied proposal，无法发现 processed token 遗失、direct fate outstanding、rollup 与 publication/terminal 不一致，仍可能给 P05-R10 发布 PASS。
- 处置要求：以 resolved config 推导 per-cycle tokens；交叉核对 receipts、updates、每版 publication direct tokens、terminal、token fates 和 rollup balance。对 hard crash 单独保留注册的一周期上界，不把 gap 伪装成 durable processed token。增加 ledger mutation tests。

### PF-03 — High — authorized replacement formal oracle 缺少容量与连续性证据

- 当前 replacement 分支只检查唯一 launch row、旧/新 instance 状态、同 stream、stream epoch 增长和旧 fence 在 replacement version 后无 applied effect（`scenario_supervisor.py:465-519`）。
- 它没有验证触发 launch 的 durable `capacity_observations`、launch row 的 scheduler/qsub transition evidence、replacement admission 的 cursor/receipt continuity、old fence rejection disposition，也没有把 replacement job attestation 加入 topology proof。
- 处置要求：把 observation→launch request→qsub receipt/history→replacement admission→stream epoch/cursor continuity→stale effect rejection串成同一 stream 的 durable evidence；topology 覆盖 replacement actor。若运行时不会自然产生可验证的 stale submit，不得伪造测试 bypass，应把形式化表述收敛为“旧 fence 无后续 durable effect”并由 transaction tests证明主动拒绝。

### PF-04 — High — authority API 仍允许省略全部 admission authorization

- `admit_incarnation()` 在 `bootstrap_slot` 与 `launch_request_id` 都缺失时，把 `stream_id` 静默当作 bootstrap slot（`authority.py:2432-2434`）。这使直接调用者能绕过“显式 bootstrap slot 或 launch request 二选一”的当前契约。
- 生产 filesystem request parser虽要求二选一，但 authority 是最终 ownership writer，不应保留隐式 bootstrap fallback；该 fallback 的主要使用者是测试 fixture。
- 处置要求：authority 强制 exact-one authorization；测试 fixture 显式传入 bootstrap slot。增加 missing/both authorization rejection test，不保留 shortcut。

### PF-05 — Medium — formal oracle test owner 没有 authorized replacement 或 ledger mutation

- 没有构造 replacement instance/launch/observation/cursor，也没有 mutation 证明 token、scheduler、capacity 或 stale-effect oracle能改变 acceptance。
- 处置要求：扩展现有 owner；不要创建新的回归文件。每项测试保留英文行为原因 docstring。

- `tools/summarize_runs.py::build_comparisons()` 只比较 Full Protocol 与 DDP/periodic-average baseline，并把 loss 与 wall time 的 20% 阈值应用到每个 Full Protocol run。
