## Findings

### Critical

None.

### High

1. The authoritative health checker can PASS a run that is not the required
   5000-step/100-step-interval formal experiment.

   Facts: `fs_diloco/baselines/health.py:139-145` accepts the manifest's own
   `max_steps` when deciding that a run completed fully. It never compares that value
   with 5000. `health.py:253-262` derives required periodic synchronization steps from
   the manifest's own `average_interval` and never requires 100. Thus a run declaring
   `max_steps=200` can be treated as a successful full run, and a periodic run declaring
   interval 200 can satisfy the checker with only the step-200 average. Existing checker
   tests always construct `max_steps=5000` and `average_interval=100`, so they do not
   cover either false-positive case.

   Impact: this violates the formal acceptance contract and can certify a job that was
   deliberately stopped at step 200 or omitted the required step-100 parameter average.

   Required fix: fail closed unless the manifest reports `max_steps=5000`; for periodic
   mode require `average_interval=100` (and preferably require the same alignment value
   for DDP statistics). Add RED tests for both mismatches.

### Medium

1. The formal PBS launchers rely on implicit Python module resolution from a virtualenv
   owned by a different worktree.

   Facts: both launchers set `PYTHON_BIN` to
   `/work/xg24i002/x10041/fsb_decoupled_diloco/.venv/bin/python` while `PROJECT_ROOT`
   may be the plan/feature worktree. Their `MPI_ENV_ARGS` do not pin `PYTHONPATH` to
   `PROJECT_ROOT`. The implementation record shows that the shared virtualenv's pytest
   console entry point resolved the primary worktree and could not import the new
   package until the plan worktree was placed on `PYTHONPATH`; all recorded torchrun
   validations also set `PYTHONPATH` explicitly.

   Inference: Python `-m` normally puts the child working directory on `sys.path`, so
   the formal launch may work, but the exact source-selection invariant was not tested
   in the form the PBS scripts use. A startup/plugin/path change could run stale code
   while the launcher records the feature worktree's source identity.

   Recommended fix: export/pass `PYTHONPATH=$PROJECT_ROOT` in both launchers and add a
   static launcher assertion or a no-preexisting-`PYTHONPATH` compute smoke.

2. The 5000-step Hugging Face final-checkpoint path has no focused test.

   Facts: `fs_diloco/baselines/train.py:189-209` stages and renames the final model and
   tokenizer, and `train.py:449-453` surrounds rank-0 saving with barriers. Tests cover
   protocol, artifacts, process groups, and health logic but do not exercise staging,
   tokenizer saving, replacement, or failure cleanup.

   Impact: a packaging/API incompatibility would only appear after all 5000 steps and
   would fail the formal job at its terminal barrier.

   Recommended fix: add a small fake `save_pretrained` model/tokenizer test proving the
   final directory is published and staging is cleaned on success/failure. This can be
   unit-only and need not simulate 5000 training steps.

### Low

1. The checker CLI does not validate positive `target_step`, `poll_seconds`, or
   `timeout_seconds` (`fs_diloco/baselines/health.py:281-308`). Invalid operator input
   can produce division errors or an invalid sleep rather than machine-readable FAIL.
   Add argument validation if the checker will be used beyond the fixed formal command.

## Correctness and invariant assessment

Facts:

- DDP accumulation correctly wraps the first `N-1` forward/backward pairs in
  `no_sync()` and performs the reducer-backed final backward before clipping and the
  optimizer step.
- The two-process test compares DDP against the same combined-batch gradient and same
  clipping operation.
- Periodic averaging uses one flattened BF16 SUM all-reduce, divides by world size, and
  copies into existing Parameter objects, so AdamW state keys, moments, scheduler state,
  and step counts are retained. The real two-node evidence records averages on both
  configured boundaries.
- Rank 0 exclusively creates the training manifest; per-rank CSV/log/heartbeat paths
  avoid concurrent writers. Source identity is checked before accepting an existing
  capture. The launchers and Python initializer both refuse existing training evidence.
- Worker exceptions are re-raised, and torchrun/mpirun use zero restarts and pipefail.
  Abrupt non-rank-0 loss is detectable through PBS liveness even when rank 0 cannot
  publish a failure summary.
- Local rank metrics and heartbeats are written before W&B logging. W&B exceptions are
  isolated from training and existing local evidence.
- The model and dataset paths, BF16/CUDA/NCCL behavior, distinct hosts, and
  MPI-supervisor-to-torchrun topology received progressively stronger runtime coverage.

Inference:

- The barrier and rank-0 final-save control flow is sound, but the untested terminal API
  path remains a material end-of-run risk.
- With the formal config enforcement defect fixed, the health checker otherwise matches
  the step-200 loss windows and synchronization acceptance rules.
