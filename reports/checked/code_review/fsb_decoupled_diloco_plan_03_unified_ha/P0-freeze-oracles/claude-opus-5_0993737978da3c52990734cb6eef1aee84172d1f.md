### High

#### H-1（并发/持久化不变量）`_fallback_publish` 的「不得认领预先存在的 final root」是**非持久**的 fail-closed：同一 identity 的第二次 retry 会静默接管它

**证据**：`scripts/miyabi/plan03_fs_capability.py:220-233`

```
:221-223  reservation_created = _link_verified(staging/".identity", reservation, expected_sha256=identity_sha256)
:229-233  try:
              final.mkdir()
          except FileExistsError:
              if reservation_created:
                  raise RuntimeError("final root predates its identity reservation")
```

`_link_verified`（`:168-181`）**只在自己成功创建 hard-link 时返回 `True`**；若 reservation 已存在且摘要相同，返回 `False`。因此该守卫依赖的是「本次进程是否创建了 reservation」这一**进程内瞬态**，而不是任何持久状态。

失败路径（`:233`）抛出前**没有清理刚刚创建的 reservation**，于是：

1. 第 1 次尝试：`final` 预先存在（遗留 run 目录 / 人工创建 / 旧版 initializer 残留），reservation 不存在 → `reservation_created=True` → mkdir `FileExistsError` → 正确 fail closed，**但 reservation 已留在磁盘上**。
2. 第 2 次尝试（同 identity，操作员重跑 init job 是最自然的动作）：`_link_verified` 命中 `FileExistsError` 且摘要相同 → `reservation_created=False` → mkdir 再次 `FileExistsError` → 守卫**不再触发** → `:234-240` 只检查 `S_ISDIR` → 继续 `link_final_identity`、逐对象 hard-link、发布 `.complete`。

发布完成后 `_fallback_visible`（`:270-298`）只校验 reservation、`.identity` 和 manifest 中列出的 3 个对象，**不校验 final 目录内是否存在其他条目**，因此这个 run 会以「complete 且 hash 全部匹配」的状态对 reader 可见，而目录里仍残留着它并不拥有的旧内容。

**次生问题（同一守卫）**：两个 **identity 相同**的 initializer 并发时，A 创建 reservation（`True`）、B 复用（`False`）、B 先 `mkdir` 成功，A 的 `mkdir` 抛 `FileExistsError` 且 `reservation_created=True` → A **误报** `final root predates its identity reservation`。同一个布尔量同时承担「异常预存目录」和「同 identity 并发对等方」两种语义，两个方向都会误判。

**probe 未覆盖**：`_probe_directory_publish_fallback:400-408` 对 orphan 场景**只调用一次** `_fallback_publish`，随后不再 retry，也不检查 `_reservation_path(orphan)` 是否被清理；`tests/test_plan03_fs_capability.py` 同样没有 orphan 分支的任何断言（该测试只断言 `crash_prefixes` / `post_visibility_prefixes` 两组）。

**失败场景**：P3 按冻结的 INIT-01 实现 initializer 后，对一个已存在于 `<shared_root>/<run_id>` 的遗留目录发起 init：第一次 job 正确失败并写下 failure；操作员重跑同一个 job，第二次**成功**并把新 run 发布到该目录之上。计划 §7 `INIT-01`「既有 final 不能被覆盖」和 §5.1.11「不能认领预先存在…的 final」两条在 retry 语义下都不成立，而 `20260808-234548_p0-shared-fs-capability_pass.json` 记录的 `"completed_root_overwrite": "fail_closed"` 会被误读为已证明该性质。

**修复建议**：
1. `:233` 抛出前，若 `reservation_created` 为真则**先 unlink 自己刚创建的 reservation 再 raise**（best-effort，失败也要把该事实带进错误信息），使 fail-closed 状态可重复。
2. 把守卫从瞬态布尔改为持久判定：`final` 存在时要求它**为空或只含本协议对象**（`os.scandir` 的条目集合 ⊆ `{".identity", ".complete"} ∪ FALLBACK_OBJECT_NAMES`），否则无条件 fail closed；这同时解决同 identity 并发误报。
3. 在 `_fallback_visible` 中把「final 目录不含协议外条目」纳入可见性判据，避免 run 坐在异物之上仍判为 complete。
4. 同步修订计划 §7 `INIT-01` 与 §5.1.11 的措辞（当前「retry 只允许恢复已有 matching reservation 且未 complete 的 final」正好把这条漏洞写成了合法路径）。

**缺失测试**：
- probe 与 `tests/test_plan03_fs_capability.py` 需要新增：orphan 失败后 **retry 仍必须失败**；失败后 `_reservation_path(orphan)` 不得残留；`final` 含协议外文件时 fail closed；同 identity 并发（先 `mkdir` 后 `link`）不得误报。

#### M-2（持久化不变量 / 运维）run 的可见性依赖 parent 目录里一个无生命周期管理的隐藏文件；该文件一旦消失，run 既不可见也不可恢复

**证据**：`scripts/miyabi/plan03_fs_capability.py:164-165, 270-281`

```
:164-165  def _reservation_path(final): return final.parent / f".{final.name}.identity-reservation"
:274-277  reservation = _reservation_path(final)
          if _sha256_regular_nofollow(reservation) != identity_sha256: return False
```

冻结的 `_fallback_visible` 把 sibling reservation 的存在与摘要匹配作为**可见性必要条件**。后果：

- 任何清理 `<shared_root>` 下点文件的运维动作（备份还原、`find -name '.*' -delete`、目录迁移不带隐藏文件、配额清理）都会让**已完成**的 run 对 reader 变为「不存在」。
- 而且不可恢复：重跑 `_fallback_publish` 会重新创建 reservation → `reservation_created=True` → `final` 已存在 → `:233` 永久抛 `final root predates its identity reservation`。
- 计划 §3.5 的 maintenance/retention 与 §7 `INIT-01` 均未定义 reservation 的保留期、GC 归属或重建路径；`<shared_root>` 每个 run 会永久多出一个隐藏文件，也未纳入 P5 迁移面清单。

**修复建议**：
1. 在计划 §7 `INIT-01` 明确 reservation 是**与 run 同生命周期的不可删对象**，并写入 §3.5 retention 的「永不 prune」集合。
2. 提供确定的重建路径：reservation 缺失但 `final/.complete` 与 `final/.identity` 校验通过时，允许**从 `final/.identity` hard-link 回 sibling reservation**（同 inode，语义安全），而不是直接 fail。
3. `_fallback_visible` 对「reservation 缺失但 final 自洽」与「reservation 不匹配」两种情形返回可区分的结果，便于 reader 报告而不是静默视为不存在。

**缺失测试**：删除 reservation 后 `_fallback_visible` 的行为、以及重建路径的 crash-prefix 覆盖，目前 probe 与 `tests/test_plan03_fs_capability.py` 均无。

## 4. 缺失测试汇总

1. **`_fallback_publish` 的 orphan / 并发分支**：retry 后仍须 fail closed、失败不得残留 reservation、final 含协议外条目须 fail closed、同 identity 并发不得误报（**H-1**）。
2. **reservation 缺失后的可见性与恢复**（**M-2**）。
3. **checker 的真实树漂移**：当前只对 `verify_inventory` 这个纯函数注入漂移，没有任何用例证明「HEAD 增删一个 fragment config → BLOCKED」（**M-1**）。
4. **`plan03_fs_capability.main()` 的非 PASS 路径**：输出命名、退出码、artifact 内容（**M-3**）。
5. **`probe()` 的 identity 字段**：`source_identity` / `recorded_at`（**M-5**）。
6. **oracle 的真实 negative 测试**：篡改 `theta_float32_le_hex` / `weights` 后主比较必须失败（**L-1**）；乱序到达 / 非零 staleness / quorum 截断的第二组 tape（**L-4**）。
7. **矩阵证据一致性**：同一 invariant 的多份 evidence 不得结论冲突（**M-4**）；`evidence_path` 必须 tracked 而非仅「可被 add 发现」（**L-10**）。
8. **`_run_arm` 的 classic 分支**：目前只有 HA 分支的计时测试（`test_ha_arm_timer_starts_before_initializer`），classic 分支的 `pre_actor_initialization_seconds≈0` 性质未被任何用例锁定。

## 5. 结论

本轮 remediation 的完成度和工程质量都很高。上一轮 4 个 High 中的 3 个（oracle 恒真、timer anchor 偏袒、checker 无断言机制）以及 9 个 Medium 中的 8 个被**实质性**修复而不是形式性绕过：oracle 现在真正经 store + filesystem 往返，`predecessor_version` 从 DB 读取，两臂各自对 golden；主 timer 前移到 fresh root 之前并把 HA initializer 计入，workload coverage/signature 在统计前 fail-closed；per-actor 文件输出 + `kill` 后 `wait` 消除了 pipe 死锁与僵尸；FS fallback 从「逐字节比较 + 4 个 crash prefix」升级为「hashed manifest + 15 step 全枚举 + pre/post visibility 分组 + `O_NOFOLLOW`/`S_ISREG`」；RED 的 `raises=AssertionError` 与 `--runxfail` 原始 log 入库让证据可复现。三次连败后的全面审查文档（`code_review.md` 新增 34 行）在数据流、状态边界、候选方案对比上写得很清楚，是可以作为后续 phase 范本的。

阻止本阶段收口的是两类问题：

1. **一个 High**：新的 FS fallback 把「不得认领预先存在的 final root」建立在**进程内瞬态布尔**上，并且在 fail-closed 路径上不清理自己创建的 reservation，导致第二次 retry 会静默接管该目录（同时对同 identity 并发误报）。这是本轮**新引入**的窗口，而 INIT-01 是要被 P3 逐字实现的冻结契约，现在修的成本最低。
2. **两个与「冻结证据的可信度」直接相关的 Medium**：唯一接入批处理的 P0-SURFACE 门禁在内容维度上恒为 PASS（**M-1**），以及被证伪的旧 FS artifact 仍并列作为同一 invariant 的通过证据（**M-4**）。此外 `_pass.json` 预命名 + 探测临时目录落在已放行的证据目录内（**M-3**）、reservation 生命周期未定义（**M-2**）、新 artifact 丢失 source binding（**M-5**）都会在后续 phase 放大。

与另一位 reviewer（gpt-5.6-sol）的差异：其 Medium（`--expect` 丢失 `differences` 明细通道）我判为 **Low**——`differences` 只是 `counts`/`manifest_sha256` 这类粗粒度标签，且 checker 是可在登录节点秒级重跑的只读工具，诊断成本有限；真正的问题是该门禁在内容维度上不会 BLOCKED（我的 **M-1**）。其 Low（oracle mutation 测试不走比较路径）我完全同意，见 **L-1**。

按 `plans/AGENTS.md` 的处置规则，`High` 阻止完成，`Medium` 必须修复或以充分证据明确延期。
