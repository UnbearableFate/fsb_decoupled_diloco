# Learner 发布后局部差值重基方案

## 1. 目标与状态

本方案在 full learner 中引入一种实验性的 `rebase_post_publish_delta` global adoption 策略，用于减少较快 learner 在等待新版 global checkpoint 时损失的、尚未发布的本地训练进度。

实现位于分支 `feature/learner-local-delta-rebase`，基线 commit 为 `bf6264fd346f4d4a7e347aaab5976011b3a6376a`。本方案只作用于 full 模式，不修改 fragment adoption 语义。

需要特别明确：learner **不常驻**一份 CPU FP32 reference。reference 只在一次发布后的首次 latest 检查没有发现新版时创建，并在发现首个新版、完成一次 rebase 后立即释放。如果发布后的首次检查已经发现新版，则根本不创建 CPU FP32 reference。

## 2. 动机

原 full learner 的行为是：

```text
发布 proposal
→ 检查一次 latest
→ 没有新版时不等待，直接继续本地训练
→ 后续采用新版时用 global checkpoint 整体覆盖本地模型
```

这一行为保持了 learner goodput，但在发布与新版 global 可见之间完成的 optimizer steps 会在整体覆盖时丢失。新方案将“已经发布的参数”和“发布后新增的本地进度”分开：已经发布的部分视为移交给 syncer，发布后新增的局部差值在新版 global 到达时迁移到新基点。

## 3. 精确状态机

设 learner 发布时的本地参数为 `x_local,t`，发现的新版 global 参数为 `x_global,new`。

### 3.1 发布后的第一次检查

learner 仍按 `io.tensor_dtype` 构造和发布 proposal；当前正式 5000-step 配置使用 BF16 payload。发布完成后立即无阻塞读取一次 `latest.json`：

```text
if 存在比 last_loaded_global_version 更新的 global:
    local ← x_global,new
    不创建 CPU FP32 reference
    重建 inner optimizer 和 LR scheduler
else:
    将当前 x_local,t flatten 为 CPU FP32 reference
    carried_delta_tokens ← 0
    进入等待首个新版的 step-wise poll 状态
```

第一次检查已有新版时，发布后尚未发生新的 optimizer step，因此直接采用新版与计算零差值等价，同时避免无意义地创建 CPU reference。

### 3.2 等待期间的本地训练

只有 CPU reference 存在时，learner 才在每次完整 `optimizer.step()` 和 `scheduler.step()` 后无阻塞检查 `latest.json`：

```text
x_local ← optimizer_step(x_local)
carried_delta_tokens += step_tokens

if 没有新版:
    继续下一次本地训练
else:
    delta_local = x_local - x_local,t
    x_local = x_global,new + delta_local
    last_loaded_global_version = new_version
    base_global_version = new_version
    tokens_since_global_load = carried_delta_tokens
    释放 CPU FP32 reference
    清零 carried_delta_tokens
    重建 inner optimizer 和 LR scheduler
```

rebase 完成后停止逐 optimizer-step 轮询。下一次是否再次建立 reference，要等到 learner 完成下一次 proposal 发布并执行新的首次 latest 检查后决定。

### 3.3 下一次发布

如果直到下一个上传周期仍没有发现新版，learner 会先释放旧 reference，再发布包含当前全部本地进度的新 proposal。发布完成后重新执行“首次 latest 检查”：有新版则直接采用；没有新版才用刚发布的当前参数建立新的临时 CPU FP32 reference。

因此每个 learner 同时最多存在一份临时 reference，且 reference 的生命周期不跨越下一次 proposal 发布。

## 4. 参数、optimizer 与计量语义

### 参数语义

- proposal 仍然是绝对参数快照，不改为上传 delta；
- rebase delta 只在 learner 本地计算，不进入共享存储协议；
- CPU reference 使用 FP32，避免 BF16 上传量化参与差值计算；
- global checkpoint 和当前本地模型在 CPU FP32 中完成差值合成，写回模型时再转换为模型参数 dtype。

### Optimizer 与 scheduler

无论是发布后立即采用新版，还是等待期间完成 rebase，均保持现有语义：

- 重建 AdamW；
- 清除旧 optimizer moments；
- 重建并重置 linear-warmup + cosine scheduler。

本轮只研究参数差值迁移，不同时引入 optimizer-state 迁移，避免无法区分参数 rebase 与 moments 延续的影响。

### Base 与 token 计量

- 区间开始时，`base_global_version` 取当前已加载 global version；
- 如果区间中途完成 rebase，`base_global_version` 更新为实际采用的新版本；
- `tokens_since_global_load` 在 rebase 后设置为 `carried_delta_tokens`，因为这些 token 对应的参数差值被保留到了新版 global 上；
- 发布后立即直接采用新版时没有 carried delta，`tokens_since_global_load` 清零。

## 5. 配置接口

新增配置：

```yaml
learner:
  poll_latest_during_inner_steps: true
  adopt_global_after_upload: true
  global_adoption_strategy: rebase_post_publish_delta
```

`global_adoption_strategy` 支持：

- `replace`：原始整体替换行为，默认值；
- `rebase_post_publish_delta`：本方案的条件式临时 reference 行为。

配置解析器执行以下 fail-fast 校验：

- `rebase_post_publish_delta` 只允许 full learner；
- 必须同时启用 `adopt_global_after_upload=true`；
- 必须同时启用 `poll_latest_during_inner_steps=true`。

正式 5000-step 配置同时保持：

```yaml
training:
  max_local_steps: 5000
  inner_steps: 100
  precision: bf16

sync:
  max_staleness_versions: 2

io:
  tensor_dtype: bfloat16

inner_optimizer:
  scheduler: cosine
  warmup_steps: 100
```

## 6. 内存与 I/O 边界

- 发布 payload 仍按 BF16 构造，不为了本方案把所有上传 staging 改成 FP32；
- 发布后第一次检查已有新版时，不构造 CPU FP32 reference；
- 只有第一次检查没有新版时，才额外保存一份模型大小的 CPU FP32 reference；
- rebase 时临时物化当前本地 FP32 向量和新版 global FP32 向量；
- rebase 完成后立即释放 reference 和临时向量；
- step-wise `latest.json` 读取只发生在 reference 存活期间，不贯穿 learner 的全部 5000 steps。

后续实验需要分别统计 reference 建立次数、实际 rebase 次数、reference 等待步数以及 learner CPU 内存峰值，不能把一次模型大小的 reference 误报为全程常驻开销。

## 7. 事件与可观测性

新增或复用以下 learner 事件：

- `local_rebase_anchor_saved`：首次检查无新版，记录 `update_id`、`base_global_version` 和 `anchor_bytes`；
- `global_rebased`：等待期间发现新版，记录前后版本、anchor update ID、carried tokens 和 local delta norm；
- `global_adopted_after_publish`：发布后的首次检查已有新版，直接采用且未保留 reference；
- `global_adopted`：兼容既有 adoption 统计；
- `inner_optimizer_reset`：确认 optimizer/scheduler 已按现有语义重建。

分析时至少应形成以下计数：

```text
anchors_saved
rebases_completed
immediate_adoptions
anchors_replaced_by_next_publish
carried_delta_tokens distribution
local_delta_norm distribution
```

其中 `anchors_saved - rebases_completed` 不能直接解释为泄漏；部分 reference 会在下一次 proposal 发布时被新发布点替代，或随 learner 正常结束而释放。

## 8. Run 配置快照

为保证实验可复现，新 run 初始化会把解析并应用 CLI 覆盖后的完整配置同时原子写入：

```text
<shared_root>/run_config.resolved.yaml
<shared_root>/control/run_config.resolved.yaml
```

两份文件内容一致。run 根副本用于直接检查实验参数；control 副本保留给 resume 和已有工具。配置快照包含本方案的 adoption strategy、BF16、staleness、scheduler、run ID 和 shared root 等最终值。

## 11. 风险与后续研究

### 发布即移交所有权

本方案把 `x_local,t` 视为发布后已移交给 syncer。若该 proposal 最终被 latest-wins 覆盖、superseded 或 too-stale，发布前的那段本地进度可能既没有进入 global，也不会继续保留在 learner 后续轨迹中。这是本实验必须量化的主要风险。

需要把 `local_rebase_anchor_saved.update_id` 与最终 proposal 状态关联，区分：

- anchor proposal 最终 applied；
- anchor proposal 被后续 proposal superseded；
- anchor proposal 因 staleness 丢弃；
- learner 在 proposal 结果明确前已经采用其他 global。

### Optimizer state 不迁移

当前只迁移参数差值，采用 global 后重置 AdamW moments 和 scheduler。若实验显示参数 rebase 有收益，再单独研究 moments 的保留、重置或衰减，不应在本轮同时改变。

### 差值尺度与训练质量

`x_global,new + delta_local` 是参数空间近似，不保证在较大 LR、较长等待或多个异步更新下保持优化等价。应结合 delta norm、等待步数、loss spike 和 validation perplexity 判断，而不能只观察训练 loss。

### 与 bounded state 的关系

CPU reference 是 learner 进程内的临时状态，不写入共享 run 协议，也不改变 current-only checkpoint/GC 规则。若未来要求 learner 进程重启后恢复这段未发布 delta，则需要为 reference 和 optimizer state设计新的持久化语义，本轮不覆盖。
