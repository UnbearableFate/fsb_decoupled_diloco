Deep System / Subsystem Code Review

Deeply review all code recursively under:

<TARGET_PATH>

Treat the current repository state as the implementation to review. Review the target as a complete system/subsystem rather than as isolated files.

Analysis approach

Use CodeGraph proactively to understand the code structure and validate findings. In particular:

* identify important entry points and core symbols;
* trace inbound and outbound call chains across files and modules;
* identify callers, callees, implementations, interfaces, and shared state involved in important execution paths;
* follow dependencies beyond <TARGET_PATH> when they affect behavior inside the target;
* determine the impact radius of suspicious or problematic code;
* trace affected execution paths through multiple layers rather than stopping at the local function;
* identify tests and components that exercise or depend on the affected paths.

Use Ruff, tests, static analysis, repository search, and any other available tools as needed to investigate and validate findings.

Do not rely solely on textual search when CodeGraph can provide a more reliable view of symbol relationships and call/dependency chains.

Before reporting issues, build a working understanding of:

* architecture and component responsibilities;
* important execution and data-flow paths;
* state ownership and lifecycle;
* invariants and consistency requirements;
* cross-module dependencies and interfaces;
* persistence/recovery behavior where applicable;
* test coverage of critical behavior.

Review focus

Focus on substantive problems:

* correctness and regressions;
* broken invariants;
* concurrency, distributed-system, lifecycle, and recovery issues;
* architectural flaws and unclear responsibility or state ownership;
* duplicated sources of truth;
* incorrect or fragile interactions across module boundaries;
* unnecessary complexity, legacy code, dead code, and obsolete compatibility paths;
* meaningful test gaps;
* performance, resource-usage, I/O, and scalability problems.

Do not perform a superficial file-by-file style review.

Review important behavior end-to-end. When a potential problem is found in one function or module, use CodeGraph and repository inspection to trace its callers, callees, state dependencies, and downstream effects before deciding whether it is a real finding.

Finding validation

For every candidate finding:

1. identify the relevant symbol(s) and execution path;
2. trace callers/callees and cross-module interactions with CodeGraph where applicable;
3. inspect relevant state transitions, guards, invariants, and failure paths;
4. inspect tests that cover or should cover the behavior;
5. determine the actual impact radius;
6. actively try to disprove the finding before reporting it.

Do not report speculative issues merely because something looks suspicious locally.

Prefer a small number of high-confidence, high-value findings over many weak observations.

Output

For each finding provide:

* Severity: CRITICAL / HIGH / MEDIUM / LOW
* Location: exact file and line/symbol
* Problem: what is wrong
* Evidence: concrete code and execution/call-chain evidence
* Impact: actual failure mode and affected components
* Recommended fix: preferably addressing the root cause rather than adding a workaround

Where relevant, explicitly include the affected chain, for example:

entry point → caller → affected function → state/dependency → downstream consumer

Finally summarize:

1. overall architecture quality;
2. major cross-module or call-chain risks;
3. simplification/deletion opportunities;
4. important missing tests;
5. overall verdict.

Do not invent findings to populate sections with no substantive issues.
