# Full Reference、持久 SQLite 与有界状态实施计划

使用skill `miyabi-development`

读取AGENTS.md和plans/imp_plans/AGENTS.md作为实施规范.

## 1. 总体设计

### 权威关系

```text
不可变 checkpoint payload
        ↓
持久 SQLite transaction：唯一提交点
        ↓
latest.json：供 learner 查询、可由 SQLite 重建的缓存
```

故障模型：

- 进程、节点和 PBS 作业可能退出；
- 共享文件系统中的已提交数据不会丢失或损坏；
- 每个 run 同时只有一个 active syncer；
- 本轮完整闭合 full 模式；fragment 使用持久 DB、取消 dump，但 fragment resume 后续单独实施；
- full reference 正式实验使用 fresh-only，事务实现仍支持已有 staleness 配置。

采用以下默认决策：

- 不兼容现有“节点本地 SQLite + DB dump”运行，不提供迁移、自动回退或 dump 恢复路径；
- terminal drain 允许低于正常 quorum 的尾部合并，proposal 耗尽后用 `input_exhausted` 正常结束；
- SQLite 使用 `journal_mode=DELETE`、`synchronous=FULL`，不在共享文件系统上使用 WAL。
- 所有 full、fragment、debug、smoke 和正式实验统一使用 current-only GC，不保留旧 checkpoint、终态 proposal tensor、processed/dropped payload 或其他冗余二进制副本。

## 2. 协议和接口修改

### 持久 SQLite

- 数据库固定为 `<shared_root>/control/syncer_metadata.sqlite3`。
- 删除运行协议中的 `sqlite_local_dir`、`resume_db_dump`、`resume_version`、`db_dump_every_versions`。
- `init.resume=false` 遇到已有 committed version 时拒绝启动；`init.resume=true` 要求 DB 中存在 committed version。
- 不再创建 DB dump，不再在退出时 backup。
- 分析工具只读取共享 FS 上的持久 DB，不搜索或读取 DB dump。
- 现有仅包含本地 SQLite 或 DB dump 的 run 保持原样，但不属于本轮 resume、分析或迁移范围。

### Full proposal 可见面

每个 learner 使用固定 metadata 指针：

```text
updates/latest/learner_000.json
updates/payloads/learner_000/<proposal_id>.params.safetensors
```

learner 先原子写 payload，再原子覆盖固定指针。syncer 每轮只读取固定的 M 个指针，不扫描历史 metadata。

同一 learner 新 proposal 到达时：

- 新 proposal 进入 pending；
- 旧 pending proposal 变为 superseded；
- 已 selected proposal继续保持 selected；
- 每 learner 活跃状态最多为一个 selected 加一个 pending；
- quorum 按唯一 learner 计数。

### 全局版本提交

`N → N+1` 的发布顺序固定为：

1. 原子写 `global_vN+1.safetensors`；
2. 原子写 `outer_vN+1.safetensors`；
3. 单个 SQLite transaction：
   - 插入 append-only `global_versions(N+1)`；
   - 将本次 selected proposal 标记为 applied；
   - 写入 effective weight、staleness 和累计 token；
   - 标记 superseded、too-stale 等终态 proposal；
4. transaction 成功后原子重写 `latest.json`；
5. 执行归档、DB pruning 和 artifact GC。

SQLite transaction 校验：

- 当前最大 committed version 为 `N`；
- 目标版本为 `N+1`；
- 所有 selected ID 仍处于 selected；
- proposal 来自不同 learner；
- base version 不在未来且满足当前 staleness 策略；
- 同一版本无法重复插入。

### Resume

syncer resume 固定执行：

1. 打开持久 DB并运行 `integrity_check`；
2. 校验 run identity 和 protocol/schema version；
3. 查询最大 committed global version；
4. 验证其 weight、outer state 和 parameter index；
5. 验证 weight 中的参数与 outer checkpoint 携带的 theta 一致；
6. 把遗留 selected proposal重置为 pending；
7. 用 DB 权威行重建 `latest.json`，无论原文件缺失、损坏、落后或超前；
8. 清理未被 DB 引用的 global orphan；
9. 完成未结束的归档与 GC；
10. 继续下一次 merge。

DB 指向缺失或不匹配 checkpoint 时 fail closed，不自动退回旧版本。

### 有界状态

- 删除可配置的多版本 retention；full 模式始终只保留 SQLite 当前 committed version 对应的一份 weight 和一份 outer state。
- fragment 模式始终只保留每个 fragment 当前 version 对应的一份 weight 和一份 outer state，以及 `latest.json` 当前引用的一份 materialized full checkpoint。
- 新 global/fragment version 完成 SQLite commit 并更新 `latest.json` 后，前一版本立即进入 GC，不为回滚、人工恢复或评估额外保留历史 checkpoint。
- 旧 global version 摘要写入 `metrics/global_version_history.jsonl` 后从活跃 DB 删除。
- applied/dropped proposal 完整摘要写入 `metrics/update_history.jsonl`，随后从活跃 DB 删除。
- archive 写入并 fsync 成功后才删除 DB 行；若中断，允许重复归档，分析时按 version/update ID 去重。
- syncer 不在归档或 GC 失败后继续生成新版本；重启后先完成维护。
- proposal payload 的 live set只由 DB 中 pending/selected 行和正在完成 pointer publication 的宽限期对象决定；fixed pointer 本身是小型控制记录，不构成保留其终态 tensor 的理由。
- SQLite 为每个 learner 记录最后已观察/消费的 proposal identity；即使 fixed pointer 暂时仍指向已完成 proposal，syncer 也能忽略该记录并删除对应 tensor，直到 learner 用新 proposal 原子覆盖 pointer。
- 新近、尚未被 pointer 引用的 payload 在孤儿宽限期内保留；宽限期取 `max(2×heartbeat interval, 2×scan interval)`。
- learner 不再自行按 local step 删除 full proposal，artifact 生命周期统一由 syncer 管理。
- GC 只依据 DB/reference live set，不依据文件名中的最大版本，避免高版本 orphan 挤掉当前 committed checkpoint。
- applied、dropped、superseded、too-stale 和 missing-file proposal 一旦完成 metadata 归档，其 tensor 立即删除；不创建 processed/dropped payload 目录副本。
- 每次启动、每次成功 commit 后和正常退出前都执行同一幂等 GC；中断后重启重新计算 live set，不恢复已淘汰历史版本。
- 日志、metrics 和只含小型结构化字段的 history JSONL 作为研究证据保留；它们不包含模型、optimizer 或 proposal tensor，不属于冗余 payload。
- 未来如果 stale displacement 需要旧 base checkpoint，需要另行修改本策略；本轮 current-only GC 不保留 base history。

### Terminal drain

当所有预期 learner 的最终 heartbeat 都是 stopped 时，输入被视为关闭：

1. 再次摄取全部固定 proposal 指针；
2. 等待一次 terminal visibility grace；
3. 正常处理达到 quorum 的 proposal；
4. 对剩余 eligible distinct proposal允许低于 quorum 的尾部 merge；
5. 无 eligible proposal且未达到 outer target 时，以 `input_exhausted` 结束；
6. dead/stale 但未声明 stopped 的 learner 不视为输入关闭，继续使用 liveness/no-progress 语义。

terminal drain 只消费当前 staleness 策略允许的 proposal，不再无条件选择全部 pending。

## 3. Loop Engineering 实施循环

| Loop | SPECIFY/RED | IMPLEMENT/GREEN | HARDEN、CHECK、PERSIST |
| --- | --- | --- | --- |
| L0 共享 SQLite 探针 | 建立共享 FS SQLite transaction、kill/reopen 和跨节点读取测试 | 实现独立 shared-FS SQLite stress probe | 在 Miyabi 1 节点和2节点验证 transaction、kill/reopen、跨节点可见性；结果写入统一报告 |
| L1 持久 DB与配置 | 路径、旧配置字段、dump 创建、分析器数据源测试先失败 | 固定 DB 路径，切换 DELETE/FULL，删除 runtime dump和本地 DB参数 | 检查所有配置、PBS、README 和运维文档无运行时 dump/local DB语义 |
| L2 原子 global transaction | rollback、重复版本、错误 predecessor、selected 不完整测试先失败 | 实现 initial commit 和 `commit_full_merge` 单事务 | 注入事务内部异常，确认 DB、proposal 状态和 global version整体回滚 |
| L3 DB-first resume | latest 缺失、损坏、落后、超前及 selected 遗留测试先失败 | resume 改为查询 DB、验证 checkpoint、重建 latest | 增加 checkpoint mismatch、DB 空、DB损坏、orphan 高版本等反例 |
| L4 固定 proposal 与有界状态 | O(history) discovery、重复计票、GC race、current-only retention 和1000-cycle 增长测试先失败 | 固定 learner pointer、latest-wins ingestion、proposal frontier、归档、pruning、引用驱动 GC | 检查所有模式只保留 current checkpoint、终态 tensor 为零、archive 去重和 crash 后维护恢复 |
| L5 Terminal drain | 复现“learner 全停、目标差一步、无 proposal、持续 quorum wait” | 实现 input-closed、terminal grace、partial drain 和 `input_exhausted` | 覆盖严格 eligible、future base、迟到 pointer、dead 但未 stopped 等情况 |
| L6 集成和集群验证 | 先冻结当前 full 50×10 与 5000-step 观测口径 | 更新 smoke/PBS/analysis/telemetry | 按 1 节点→2节点→9节点验证，独立 Checker 复核不变量，更新全部文档和研究计划 |

每个 loop 的 PERSIST 内容包括：失败测试、通过命令、原始日志、run 配置、DB 查询结果、artifact 列表和下一项未解决差距。

### Publication crash matrix

每个注入点使用 tiny full pipeline 重复 10 次：

| 注入点 | 恢复后的期望 |
| --- | --- |
| 权重临时文件写入中 | DB/latest 保持 N，临时文件可清理 |
| 权重完成、outer 未完成 | DB/latest 保持 N，权重成为 orphan |
| 两个 payload 完成、DB 未提交 | DB/latest 保持 N，两个 payload成为 orphan |
| SQLite transaction 中 | transaction 整体回滚 |
| DB commit 后、latest 前 | DB 为 N+1；重启后 latest 自动修复为 N+1 |
| latest 更新后 | DB/latest 均为 N+1 |

所有场景还需满足：

- `integrity_check=ok`；
- learner 从未看到引用缺失 payload 的 latest；
- selected proposal不被重复应用；
- 恢复后下一次 merge得到 N+2；
- 无人工修改 DB 或 latest。

## 5. Miyabi 验证阶梯

### Login 节点静态检查

- 只运行 `git diff --check`、`ruff check`、配置检查和 `bash -n scripts/miyabi/*.pbs`；
- 不运行 pytest、torch import、模型加载或训练。

通过条件：静态检查全部通过，所有 PBS 脚本含真实 group ID，且不再传递 `SYNCER_DB_DIR/--sqlite-local-dir`。

### 1 节点 compute allocation

依次运行：

1. focused SQLite/store/resume/retention tests；
2. 全部 pytest；
3. 10,000-transaction shared FS probe；
4. tiny full 2-learner smoke；
5. 六个 publication failpoint 的 kill/restart 矩阵；
6. terminal drain synthetic cases。

通过条件：全部测试通过、DB integrity 正常、无 dump、无重复应用、所有 run 有一致 stop/summary/latest/DB。

### 2 节点 compute allocation

节点 A运行并提交若干 full version后终止 syncer，节点 B从同一 shared root启动 syncer。

通过条件：

- 节点 B只读取持久 DB即可恢复；
- latest 自动重建；
- learner无需修改 proposal；
- 至少再成功提交一个新版本；
- DB integrity、版本连续性和 proposal exactly-once全部通过。

### 9 节点 batch

运行：

1. full BF16 50×10；
2. 提交修订后的 full 5000-step/50-outer-step 长运行，并观察其启动阶段。

50×10 通过条件：

- 8 learner、10 committed merge；
- SQLite、latest、summary均为版本10；
- 没有 error、no-progress timeout或 dump；
- global rows=1、只保留版本10的 weight/outer、active updates ≤16、终态 proposal tensor=0；
- SQLite commit p95低于2秒；
- SQLite commit与状态维护总时间低于完整训练时间的5%。

5000-step 阶段性交接条件：

- PBS job 已成功提交并进入运行状态；
- 从初始 `v0` 之后连续观察到至少 5 次新的 global commit，即 DB 已正常提交到不低于 `v5`；
- 这 5 次 commit 中 SQLite 最大 committed version、`latest.json` 和对应 weight/outer payload 一致；
- 到达 `v5` 时只保留 `v5` 的 full weight/outer，`v0` 至 `v4` 的 checkpoint 和已经终态化的 proposal tensor均已被 GC；
- proposal selection、merge、SQLite transaction、latest 更新和 learner adoption 均持续前进；
- 观察期间没有 error、DB integrity 错误、重复版本、缺失 checkpoint 或 no-progress timeout；
- agent 记录 PBS job ID、run ID、shared root、当前 committed version、`qstat` 状态和关键日志路径；
- 达到上述条件后，agent 可以暂时退出当前任务并等待用户下一步指示，不取消或终止仍在运行的 5000-step job，也不继续等待完整训练结束；
- 完整 5000-step 的 terminal drain、有界状态和最终结果验收留到用户下一次要求继续观察时完成。

## 6. Checker 与文档同步

独立 Checker 从以下不变量反推遗漏：

- 删除 `latest.json` 后仍可仅凭 DB恢复；
- 删除 DB 后仅凭 latest无法 resume；
- DB commit之前没有新版本对 learner可见；
- DB commit之后 latest可以任意重建；
- 当前 checkpoint不会因高版本 orphan被清理；
- active discovery和 active DB规模不依赖历史 update数；
- terminal drain不绕过 base/staleness规则。

Checker 输出只允许：

- `PASS`
- `PASS_WITH_FOLLOWUPS`
- `BLOCKED`
